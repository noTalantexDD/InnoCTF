# 06. SSH и защита доступа к vulnbox

[Оглавление](./README.md) · [Сеть и прокси](./05-network-and-proxy.md) · [Инвентарь сервисов](./07-service-inventory.md)

На A/D через SSH ты можешь чинить приложения, смотреть логи и скачивать копии. Опаснее всего поменять правила входа, закрыть рабочую вкладку и выяснить, что новый вход уже не работает. Поэтому действуем по порядку: **первый сеанс → рабочий ключ → резервная копия → проверка конфига → применение → два теста нового соединения**.

## 1. Что подготовить

| Что | Учебное значение | Где взять своё |
|---|---|---|
| Адрес своего сервера | `10.2.17.2` | Из выдачи организаторов |
| SSH-порт | `22` | Из выдачи. В примерах стандартный порт |
| Учётка | `player` | Из выдачи. Иногда выдают только `root` |
| Ключ участника | `~/.ssh/innoctf_ed25519` | Создан на ПК по [главе 04](./04-workstation.md) |
| Резервный доступ | Консоль площадки | По правилам турнира |
| Ответственный | Один человек ведёт изменения SSH | Договоритесь в команде до правок |

Дальше учётка `player` имеет разрешение на `sudo`. Если выдали `root`, подставь его и выполняй административные команды на сервере без `sudo`. Linux и WSL подходят для Bash-примеров. В PowerShell SSH-команды тоже работают при установленном OpenSSH, а путь к приватному ключу берётся из профиля Windows.

**Вкладка A** — первоначальный сеанс на сервере, который оставляешь открытым. **Вкладка ПК** — отдельный локальный терминал для новых подключений. Если на сервере потерялись, `hostname` и `whoami` подскажут машину и пользователя.

## 2. Зайди впервые и подтверди сервер

**Где:** рабочий ПК, будущая вкладка A.

```bash
ssh -p 22 player@10.2.17.2
```

`-p` задаёт порт, `player@…` означает «войти под player на указанную машину». Если клиент впервые видит сервер, он может показать отпечаток ключа хоста. Сверь его с данными, которые дали организаторы, или с доверенной консолью. Ключ хоста удостоверяет сервер. Твой пользовательский ключ затем удостоверит тебя для сервера.

Если уже известный отпечаток изменился и SSH предупреждает, что сервер другой, сначала сверь IP, порт и новую выдачу. Удалять запись из `known_hosts` наугад не нужно.

После входа, **во вкладке A на сервере**:

```bash
hostname
whoami
id
sudo -v
```

`id` показывает UID и группы. `sudo -v` проверяет, доступно ли подтверждение полномочий, и может запросить пароль. Даже при успехе конкретная команда может быть ограничена политикой sudo. Если `sudo` не разрешён, выясни, какая учётка должна администрировать сервер.

Если выдан временный пароль и по правилам его нужно менять, запусти `passwd` на сервере под целевой учёткой. Обычная последовательность — старый пароль, новый, повтор нового. Пустой вывод при вводе пароля нормален. Если команда общая, согласуйте смену пароля и порядок передачи через предусмотренное место для секретов.

## 3. Добавь свой публичный ключ

Оставь вкладку A. **На ПК, в другом терминале**:

```bash
ssh-copy-id -i "$HOME/.ssh/innoctf_ed25519.pub" -p 22 player@10.2.17.2
```

Команда добавляет содержимое `.pub` на сервер. Может попросить текущий пароль учётки. Приватный файл на сервер не копируется. Если `ssh-copy-id` отсутствует или площадка использует нестандартное хранилище ключей, воспользуйся выданным порядком.

При стандартном `~/.ssh/authorized_keys` ручной вариант выполняется **на сервере под целевым пользователем**, без `sudo`:

```bash
mkdir -p "$HOME/.ssh"
chmod 700 "$HOME/.ssh"
touch "$HOME/.ssh/authorized_keys"
chmod 600 "$HOME/.ssh/authorized_keys"
nano "$HOME/.ssh/authorized_keys"
```

`touch` создаёт отсутствующий файл и сохраняет содержимое существующего. В редакторе добавь публичный ключ отдельной строкой. В Nano сохранить и выйти можно через `Ctrl+O` → Enter → `Ctrl+X`. При существующем файле полезно сохранить его копию до редактирования. `700` у каталога и `600` у файла оставляют доступ владельцу. Если `AuthorizedKeysFile` иной или ключи предоставляет `AuthorizedKeysCommand`, уточни способ выдачи ключей. [Настройки OpenSSH](https://man.openbsd.org/sshd_config)

### Докажи, что сработал именно ключ

**Где:** ПК, отдельный терминал. Вкладка A всё ещё открыта.

```bash
ssh -p 22 -i "$HOME/.ssh/innoctf_ed25519"   -o IdentitiesOnly=yes -o PreferredAuthentications=publickey   -o ControlPath=none player@10.2.17.2
```

| Параметр | Зачем |
|---|---|
| `-i ...` | Выбирает приватный файл на ПК |
| `IdentitiesOnly=yes` | Ограничивает список предлагаемых идентификаторов |
| `PreferredAuthentications=publickey` | Для теста выбирает аутентификацию по ключу |
| `ControlPath=none` | Отключает повторное использование уже открытого SSH-соединения |

Ключ с парольной фразой может попросить её на ПК. Это проверка приватного файла, а не пароль удалённой учётки. Внутри нового сеанса повтори `whoami` и `sudo -v`. Если каждому нужен свой ключ, проверьте вход каждого до отключения пароля. [Клиент OpenSSH](https://man.openbsd.org/ssh)

### Сверь ключи, прежде чем убирать лишние

При стандартном пути **на сервере под целевым пользователем**:

```bash
cp -a -- "$HOME/.ssh/authorized_keys" "$HOME/.ssh/authorized_keys.before-ad"
ls -ld -- "$HOME/.ssh" "$HOME/.ssh/authorized_keys"
ssh-keygen -lf "$HOME/.ssh/authorized_keys"
```

Сверь отпечатки с командами `ssh-keygen -lf` для публичных файлов участников. Перед повторным копированием выбери другое имя резервного файла, чтобы сохранить исходную версию. Если назначение ключа неизвестно, уточни у организаторов. После удаления подтверждённо лишней строки снова проверь новый вход.

Если участнику перестало пускать, верни предыдущее содержимое из вкладки A через `cp -a -- "$HOME/.ssh/authorized_keys.before-ad" "$HOME/.ssh/authorized_keys"`. Для правки этого файла перечитывать конфигурацию SSH обычно не требуется.

## 4. Посмотри действующие настройки SSH

**Где:** вкладка A на сервере. На типичной Linux-машине sshd читает `/etc/ssh/sshd_config`, но конкретный юнит может передавать свой путь или параметры.

```bash
systemctl status ssh --no-pager
sudo sshd -T | grep -Ei '^(pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication|authenticationmethods|permitrootlogin|authorizedkeysfile) '
sudo grep -niE '^[[:space:]]*(Include|Match|PubkeyAuthentication|PasswordAuthentication|KbdInteractiveAuthentication|AuthenticationMethods|PermitRootLogin)([[:space:]]|$)'   /etc/ssh/sshd_config
```

Если службы `ssh` нет, проверь `sshd`. Можно посмотреть её запуск через `systemctl cat ssh` или `systemctl cat sshd`. Если аргументы запуска указывают другой файл, проверяй тот же файл, который использует сервер. Для чтения нужных правок загляни и в файлы из `Include`.

- **`Include`** добавляет содержимое других конфигов в точке включения. Для большинства параметров OpenSSH берёт первое применимое значение, поэтому дописывание в конец может не сработать.
- **`Match`** задаёт условия для конкретного пользователя или адреса. Такую политику проверяй на параметрах реального подключения.
- **`AuthenticationMethods`** может требовать несколько способов входа. Убедись, что выбранная политика согласуется с отключением пароля.
- **`PermitRootLogin`** определяет удалённый вход под root. Если root — единственный предусмотренный административный доступ, не меняй его вслепую. [sshd_config](https://man.openbsd.org/sshd_config)

Для проверки `Match` узнай адреса через `printf '%s\n' "$SSH_CONNECTION"`. В строке идут адрес клиента, его порт, адрес сервера и порт сервера. Подставь свои значения:

```bash
sudo sshd -T -C user=player,addr=10.2.17.23,laddr=10.2.17.2,lport=22   | grep -Ei '^(pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication|authenticationmethods|permitrootlogin) '
```

При `Match Host` дополнительно передай фактическое имя клиента через `host=…`. При сложной конфигурации ответственный сверяет все учётки и типы подключения, на которые повлияет правка. [Параметры sshd](https://man.openbsd.org/sshd)

## 5. Сохрани конфиг, измени только нужное, проверь

**Где:** вкладка A. Сначала сделай отдельную копию каждого затрагиваемого файла. Ниже пример для основного конфига. Если копия с таким именем уже есть, сначала выбери другое имя, чтобы не потерять прежнее рабочее состояние.

```bash
sudo cp -a -- /etc/ssh/sshd_config /etc/ssh/sshd_config.before-ad
sudoedit /etc/ssh/sshd_config
```

В действующем глобальном или подходящем условном блоке выставь:

```text
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
```

Парольный метод и интерактивный метод отключаются отдельно. `KbdInteractiveAuthentication` может также обслуживать разрешённую многофакторную схему, поэтому перед изменением учитывай требования площадки. `sudo` и вход с консоли управляются отдельно. Если правишь включаемый файл, копируй и редактируй его. Если создаёшь новый временный файл, запиши точное имя для отката.

Проверь синтаксис и итоговые значения:

```bash
sudo sshd -t &&
  sudo sshd -T | grep -Ei '^(pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication|authenticationmethods) '
```

`sshd -t` при успехе обычно молчит. В итоговом выводе ожидаются `pubkeyauthentication yes`, `passwordauthentication no` и `kbdinteractiveauthentication no`. Если есть `Match`, повтори `sshd -T -C` из предыдущего раздела. Если конфиг не проходит проверку, сначала исправь ошибку или верни копию.

Затем, если у вас юнит `ssh` и он поддерживает перечитывание:

```bash
sudo systemctl reload ssh
```

Если юнит называется `sshd`, подставь его. Если `reload` не поддерживается, сверяй штатный порядок с площадкой, прежде чем перезапускать службу. Не закрывай вкладку A и сохраняй доступ к консоли.

## 6. Проведи два теста и знай откат

1. **На ПК** снова выполни длинную команду из раздела 3 с ключом. Должен открыться новый сеанс. `whoami` и `sudo -v` проверяют учётку и запрошенные полномочия.
2. **На ПК** отдельно попробуй подключение, где ключевой метод выключен:

```bash
ssh -p 22 -o PubkeyAuthentication=no   -o PreferredAuthentications=password,keyboard-interactive   -o ControlPath=none player@10.2.17.2
```

Ожидается отказ на этапе аутентификации **без приглашения ввести пароль учётки**. Если видишь приглашение, прерви тест и проверь эффективную конфигурацию. Таймаут здесь ничего не доказывает.

**Если новый сеанс сломался:** во вкладке A восстанови изменённые файлы. Для примера с основным конфигом:

```bash
sudo cp -a -- /etc/ssh/sshd_config.before-ad /etc/ssh/sshd_config
sudo sshd -t && sudo systemctl reload ssh
```

Если ты добавил новый включаемый файл, выведи именно его из области действия `Include`. Откат основного файла без этого шага может оставить новую политику. Если изменял существующий включаемый файл, верни его копию. После синтаксической проверки повтори `reload` и новый вход. Потеряна вкладка A — используй доверенную консоль площадки.

| Симптом | Первый осмысленный шаг |
|---|---|
| `Connection timed out` | Адрес, порт, фаза игры и маршрут с ПК |
| `Connection refused` | Через консоль проверь, слушает ли SSH нужный TCP-порт |
| `Permission denied (publickey)` | Логин, путь к ключу на ПК, владельца и права `authorized_keys`, эффективные `Match` |
| `REMOTE HOST IDENTIFICATION HAS CHANGED` | Подтверди новый отпечаток через площадку и сверь адрес |
| Ключ работает, `sudo` не работает | Уточни выданную учётку и её права до закрытия запасного входа |

## 7. Перед тем как закрыть вкладку A

- [ ] Новый сеанс по ключу проверен отдельно, у ответственного работают нужные права.
- [ ] Команда знает, какой доступ предусмотрен для каждого участника.
- [ ] Парольные методы действительно не предлагаются после изменения, если этого требует ваша схема.
- [ ] Записаны затронутые конфиги, путь к копии и способ открыть консоль.
- [ ] Дальше можно переходить к [инвентарю сервисов](./07-service-inventory.md).
