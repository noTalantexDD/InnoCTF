# 07. Инвентарь сервисов на своём vulnbox

[Оглавление](./README.md) · [SSH и защита доступа](./06-ssh-and-hardening.md) · [Сеть и прокси](./05-network-and-proxy.md)

В инвентаре нужно ответить на один вопрос: **что именно работает за игровым адресом и где лежат данные, которые нельзя потерять?** Для каждого сервиса пройди цепочку: **порт → процесс или прокси → способ запуска → код и конфиг → хранилище → штатный тест**. Если найден только первый элемент, приложение ещё не разобрано.

В примерах `10.2.17.2` — условный адрес **вашего** vulnbox, `8080` — условный внешний порт «Заметок». Имена служб, контейнеров и пути придуманы для разбора. Сверяй их с выдачей площадки и выводом своего сервера.

## 1. Начни с листа организаторов

**До команд** выпиши игровые сервисы и известные внешние порты. Это важно, потому что на сервере могут одновременно слушать SSH, внутренняя база, прокси и несколько приложений. Прослушиваемый порт сам по себе ничего не говорит о том, должен ли он быть доступен с рабочего ПК.

Во время первого обхода заполняй карточку. Если ответа пока нет, укажи `не выяснено`.

| Что записать | Пример для «Заметок» |
|---|---|
| Видимый адрес и порт | `http://10.2.17.2:8080/` |
| Протокол и путь | HTTP, вход и пользовательская страница |
| Первое звено, которое получает запрос | Публикация порта Docker или обратный прокси |
| Как запускается приложение | Проект Compose `notes`, сервис `web` |
| Где находятся код и конфиг | Допустим, `/opt/notes`. Подтвердить по конфигу запуска |
| Где данные | Отдельный контейнер БД с именованным томом. Записать имя и точку назначения |
| Обычный пользовательский сценарий | Войти, прочитать свою старую заметку, создать и прочитать новую |
| Кто отвечает | Имя участника |
| Когда проверено | Время, результат с ПК и статус Jury, если доступен |

## 2. Сними исходное состояние сервера

**Где:** SSH на своём vulnbox. Эти команды читают текущее состояние.

```bash
hostname
date -Is
ip -br address
sudo ss -lntup
systemctl list-units --type=service --state=running --no-pager
df -h
```

| Команда | Зачем | Как читать |
|---|---|---|
| `hostname` и `date -Is` | Зафиксировать машину и время | Можно связать наблюдение с журналом и результатом Jury |
| `ip -br address` | Увидеть интерфейсы и адреса | При разборе `0.0.0.0` полезно знать, какие интерфейсы существуют |
| `ss -lntup` | Показать слушающие TCP и UDP сокеты и по возможности процессы | Сопоставь локальный адрес, порт и строку процесса |
| `systemctl list-units …` | Увидеть запущенные службы systemd | Если systemd отсутствует, ориентируйся на выданную схему, процессы и контейнеры |
| `df -h` | Посмотреть занятое и свободное место по файловым системам | Для бэкапа важен раздел, на котором находится выбранная выходная папка |

Флаги `ss`: `-l` — прослушивание, `-n` — числа вместо имён служб, `-t` — TCP, `-u` — UDP, `-p` — процесс и PID, если доступны. В выводе UDP сокет часто выглядит как `UNCONN`. У UDP нет принятия TCP-соединения, но процесс может получать дейтаграммы на таком порту. [Руководство ss](https://man7.org/linux/man-pages/man8/ss.8.html)

### Как прочитать две строки

```text
tcp  LISTEN  0  128  0.0.0.0:8080  0.0.0.0:*  users:(("nginx",pid=1150,fd=6))
tcp  LISTEN  0  128  127.0.0.1:8000  0.0.0.0:*  users:(("python",pid=1402,fd=5))
```

- `0.0.0.0:8080` означает прослушивание на всех IPv4-интерфейсах. Доступ извне ещё зависит от маршрута и фильтра.
- `127.0.0.1:8000` означает прослушивание внутри этой машины. В примере `nginx` **может** проксировать запросы на этот адрес. Подтверди это в конфиге, совпадение портов само по себе ничего не устанавливает.
- `pid=1150` — идентификатор процесса. По нему можно выяснить способ запуска.
- `[::]:8080` означает прослушивание на IPv6-интерфейсах. Обработка IPv4 зависит от конфигурации сокета.

Публикация порта Docker может использовать сетевые правила. Отсутствие ожидаемого отдельного процесса в `ss` не исключает, что порт опубликован. Сверь контейнеры и схему запуска. [Публикация портов Docker](https://docs.docker.com/engine/network/port-publishing/)

## 3. Вариант A. Сервис запущен через systemd

**Где:** vulnbox. Сначала подставь PID из `ss`. Команды читают имя процесса и пытаются определить, какому юниту он принадлежит.

```bash
ps -p 1402 -o pid,ppid,user,comm
systemctl status 1402 --no-pager
```

`PPID` — идентификатор родительского процесса, `USER` — учётка, `COMM` — краткое имя. `systemctl status PID` может показать юнит, к которому относится процесс. Если он входит в контейнер, можно увидеть более общий юнит, а дальше стоит перейти к Docker. PID меняется после перезапуска, поэтому сверяй его со свежим выводом. [systemctl](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html)

Допустим, нашёлся `notes.service`. Посмотри его описание и свежие логи:

```bash
systemctl status notes.service --no-pager
systemctl show notes.service -p FragmentPath -p DropInPaths -p WorkingDirectory -p MainPID
systemctl cat notes.service
sudo journalctl -u notes.service --since "10 minutes ago" -n 50 --no-pager
```

1. **`status`** показывает текущее состояние и несколько строк журнала. `active (running)` говорит о состоянии процесса, полную работу приложения проверяй раздельно.
2. **`show`** печатает выбранные поля. `FragmentPath` — основной файл юнита. `DropInPaths` — дополнительные фрагменты. `WorkingDirectory` может указывать каталог приложения. `MainPID` — основной процесс по мнению systemd.
3. **`cat`** показывает основной файл и drop-in. Ищи `ExecStart`, параметры конфига и ссылки на файлы окружения. В них могут быть секреты. В командную карточку записывай нужные пути и имена без значений паролей и токенов.
4. **`journalctl`** читает записи одного юнита. `--since` ограничивает время, `-n 50` возвращает последние 50 подходящих строк. Сравни время ошибки с моментом своего теста. [journalctl](https://www.freedesktop.org/software/systemd/man/latest/journalctl.html)

Если сервис запущен другим менеджером, узнай его штатный способ по инструкции. В инвентаре стоит указать, откуда взял сведения, чтобы напарник мог повторить поиск.

## 4. Вариант B. Сервис запущен в Docker

**Где:** vulnbox, если у вашей учётки есть выданный Docker-доступ. Если он предоставлен через `sudo`, примеры выполняются как ниже.

```bash
sudo docker ps -a
sudo docker compose ls --all
```

- `docker ps -a` показывает работающие и остановленные контейнеры. Если смотришь только `docker ps`, остановившийся сервис может исчезнуть из списка.
- `docker compose ls --all` показывает доступные проекты Compose, включая остановленные. Если Compose отсутствует, продолжай с доступными командами Docker и документацией площадки.
- В `PORTS` запись `0.0.0.0:8080->80/tcp` означает публикацию порта `8080` хоста в `80` контейнера. Запись `80/tcp` без стрелки сама по себе не показывает публикации порта хоста. [Список контейнеров](https://docs.docker.com/reference/cli/docker/container/ls/) · [Проекты Compose](https://docs.docker.com/reference/cli/docker/compose/ls/)

Допустим, контейнер называется `notes-web`:

```bash
sudo docker port notes-web
sudo docker inspect --format 'state={{.State.Status}} image={{.Config.Image}}' notes-web
sudo docker inspect --format '{{json .Mounts}}' notes-web
sudo docker logs --since 10m --tail 50 notes-web
```

| Что читаешь | Что записать |
|---|---|
| `docker port` | Реальные опубликованные сопоставления портов у этого контейнера |
| `.State.Status` и `.Config.Image` | Состояние и имя образа |
| `.Mounts` | Что примонтировано, где источник, куда он виден внутри контейнера |
| `docker logs` | Ошибку за время своего запроса, если приложение пишет в стандартный вывод |

У `Mounts` полезны `Type`, `Name`, `Source`, `Destination` и `RW`:

- **`Type=bind`.** `Source` — путь на хосте, `Destination` — путь внутри контейнера.
- **`Type=volume`.** `Name` — имя тома, а `Destination` — куда он подключён. Для бэкапа или восстановления используй штатный порядок томов и БД.
- **`RW=false`.** У этого контейнера подключение только на чтение.
- **Список пуст.** Проверь архитектуру приложения. Данные могут лежать в отдельном контейнере БД или во внешнем хранилище. При записи в слой контейнера пересоздание может потерять данные.

Для проекта Compose найди его файл в выдаче или выводе `docker compose ls`. После перехода в нужный каталог можно посмотреть состояние контейнеров проекта:

```bash
sudo docker compose ps --all
```

Если проект запускался с несколькими файлами `-f`, нестандартным именем проекта или специальным окружением, используй тот же порядок, который указан в выдаче. Для инвентаря не нужно запускать `up`, `down` или удалять тома. [Состояние Compose](https://docs.docker.com/reference/cli/docker/compose/ps/) · [Тома Docker](https://docs.docker.com/engine/storage/volumes/)

## 5. Проверь внешнее поведение с рабочего ПК

**Где:** рабочий ПК, после выдачи доступа к своему сервису. Подставь реальный адрес и путь:

```bash
curl --noproxy '*' -sS -i --connect-timeout 4 --max-time 8   "http://10.2.17.2:8080/health"
```

Если `/health` не предусмотрен, используй известный штатный путь. Для другого протокола нужен его обычный клиент. Сначала запиши ответ конкретного маршрута, потом проверь **пользовательский сценарий**, например:

1. Войти в «Заметки» под своей тестовой учёткой.
2. Прочитать тестовую запись, которая уже была сохранена раньше.
3. Создать новую запись с учебным текстом.
4. Открыть новую запись и убедиться, что текст сохранился.
5. Записать время, порт и результат каждого действия.

Такой исходный тест пригодится при правке. Если новое создание работает, а прежняя запись исчезла, проверяй правильную БД и том. Если HTTP с ПК вообще не открывается, возвращайся к [диагностике сети](./05-network-and-proxy.md). Ошибка `404` означает, что кто-то ответил на HTTP-запрос, но указанный путь не найден. Для проверки штатной работы выбери рабочий маршрут. [Параметры curl](https://curl.se/docs/manpage.html)

### Готовый пример цепочки

| Уровень | Что установлено |
|---|---|
| Внешний вход | ПК обращается к `10.2.17.2:8080`, ответ приходит |
| Публикация | В Docker `8080->80/tcp` ведёт к веб-контейнеру |
| Запуск | `notes-web` входит в проект Compose `notes` |
| Данные | Проект подключает отдельную БД с томом `notes-data` |
| Связь между компонентами | Запросы к веб-странице работают, изменение БД затронет чтение и запись |
| Что сохранить | Конфиги запуска и приложения, имя и расположение тома, согласованный бэкап БД, если используете её |
| Чем проверить | Чтение старой учебной записи и создание новой с ПК |

## 6. Что делать с непонятным портом

Если видишь порт, которого нет в выданном списке, запиши **адрес прослушивания, протокол, владельца процесса и зависимости**. Возможны внутренняя БД, служебный агент, SSH, обратный прокси или ещё не занесённый игровой сервис.

Изменение порта или фаервола обсуждает ответственный за сеть. До него нужно узнать назначение порта, сверить правила площадки, иметь резервный доступ и повторить штатный тест после изменения. Ошибка в общей настройке может лишить доступа несколько сервисов одновременно.

О признаках сбоя сообщай в форме:

> «Заметки», 10:28. С ПК внешний 8080 отвечает, вход работает. Старая тестовая запись не открывается. В проекте виден том notes-data, проверяю, какой контейнер и путь сейчас используют.

## 7. Самопроверка

1. В `docker ps` нет «Заметок». Какая команда покажет остановленный контейнер?
2. `ss` показывает `127.0.0.1:8000`, а с ПК работает `8080`. Что проверишь?
3. Нашёл Compose-файл, в нём есть БД с томом. Достаточно ли сохранить один YAML, чтобы восстановить данные?
4. После изменения БД сайт показывает `200` и создаёт новые записи. Какой тест всё ещё нужен?
5. У кого спросить перед ограничением порта, назначение которого неясно?

<details>
<summary>Ответы</summary>

1. `docker ps -a`. Для конкретного проекта подходит `docker compose ps --all` при правильном выборе проекта.
2. Сопоставь внешний порт с опубликованным Docker-портом и прокси. `127.0.0.1` означает локальное прослушивание.
3. Нет. YAML описывает запуск, а записи могут находиться в томе или внешней БД. Нужно сохранить и проверить данные отдельно.
4. Прочитать свою учебную запись, созданную до изменения.
5. У владельца сервиса, ответственного за сеть и при необходимости у площадки. До ответа установи, что именно слушает порт.

</details>
