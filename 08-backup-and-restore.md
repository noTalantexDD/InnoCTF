# 08. Бэкапы и восстановление на A/D

[Оглавление](./README.md) · [Инвентарь сервисов](./07-service-inventory.md) · [Как читать сервис](./09-read-a-service.md)

После правки сайт «Заметки» открывается, но старая учебная запись исчезла. У тебя может быть исправная база, к которой приложение просто перестало подключаться. В таком случае нужно вернуть настройку подключения. Если база действительно повреждена, понадобится дамп или другая согласованная копия данных. Чтобы различить эти ситуации под таймером, заранее сохрани **точку исходного состояния** и проверь восстановление на отдельной копии.

## 1. Что сохранять

| Часть сервиса | Что записать в карточку | Что копировать |
|---|---|---|
| Код и файлы приложения | Каталог, версия или коммит, способ сборки | Каталог или исходники, которых достаточно для повторной сборки |
| Конфигурация | Файл запуска, включённые фрагменты, имена подготовленных переменных | Конфиги, Compose-файлы, необходимые файлы окружения и юниты systemd с сохранением доступа к секретам |
| Файлы пользователей | Путь на хосте или имя подключённого тома | Каталог загрузок, если данные согласованы и в момент копирования не меняются |
| База | Тип БД, экземпляр, имя базы, имя роли без пароля | Штатный дамп или согласованная копия для выбранной БД |
| То, чем проверите восстановление | Например, старая тестовая заметка и сценарий входа | Условие успешной проверки в журнале команды |

У Docker отдельно проверь `Mounts`. Архив каталога с `compose.yaml` описывает запуск, а данные могут лежать в отдельном томе. У systemd может быть основной юнит, drop-in и отдельный `EnvironmentFile`. Список путей возьми из [инвентаря](./07-service-inventory.md).

Если исходный контейнер запускается из образа, запиши, откуда его возьмёте при восстановлении. При закрытой сети даже точное имя образа бесполезно, если нужного образа и способа сборки больше нет. Сохраняй только то, что относится к вашему сервису и разрешено правилами площадки.

## 2. Подготовь закрытую папку на своём vulnbox

**Где:** SSH на сервере, в том терминале, где будешь выполнять следующие команды. В примерах используется Bash на Linux.

```bash
umask 077
mkdir -p -m 700 "$HOME/ad-backup"
df -h "$HOME/ad-backup"
backup_dir=$(mktemp -d "$HOME/ad-backup/notes-XXXXXX")
printf '%s\n' "$backup_dir"
```

- `umask 077` задаёт ограниченные права для новых файлов этого сеанса. Если каталог уже существовал, `mkdir` не меняет его права. Сверь их через `ls -ld "$HOME/ad-backup"`.
- `df -h` показывает свободное место именно там, где ты собираешься писать архив. Дамп БД и архивы могут занять больше места, чем кажется.
- `mktemp -d` создаёт уникальный каталог и сохраняет его имя в `backup_dir`. Если команда завершилась ошибкой или путь пустой, остановись и проверь место и права.
- `backup_dir` существует только в текущем shell. После переподключения подставь точный путь к уже созданной папке.

Подготовь пару секунд на запись в журнале: дата, время и часовой пояс, сервис, причина копирования, кто делал, что входит в комплект. Токены, пароли и сами флаги в журнал не записывай.

## 3. Сохрани код и конфиги

Ниже пример: код и статичные конфиги лежат в `/opt/notes`. Если в этом же каталоге есть активная база, сначала установи её путь и отдели нужные статичные файлы от данных. Для живой БД используй раздел 4.

**Где:** vulnbox, в сеансе с `backup_dir`. При необходимости подставь реальное имя каталога. В примере `sudo` нужен для чтения исходника, архив пишет текущий пользователь.

```bash
sudo tar -C /opt -czf - notes > "$backup_dir/notes-files.tar.gz.part" &&
  gzip -t -- "$backup_dir/notes-files.tar.gz.part" &&
  tar -tzf "$backup_dir/notes-files.tar.gz.part" > /dev/null &&
  mv -- "$backup_dir/notes-files.tar.gz.part" "$backup_dir/notes-files.tar.gz"
```

`-C /opt` меняет рабочую папку tar перед архивированием. Внутри будет путь `notes/…`. `-c` создаёт архив, `-z` включает gzip, `-f -` пишет в стандартный вывод. Перенаправление `>` сохраняет вывод в файл. `gzip -t` проверяет сжатый поток, `tar -tzf` читает список объектов. Цепочка `&&` переименует файл в финальное имя только после успеха всех шагов.

Если `tar` сообщает, что файл изменился во время чтения, не используй этот архив как подтверждённую копию. Сначала узнай, почему меняется источник, и выбери способ копирования с согласованным состоянием. Даже успешное чтение архива ещё не проверяет работоспособность восстановления.

Файлы из `/etc`, unit и drop-in, которые находятся вне `/opt/notes`, нужно сохранить отдельно. Для одиночного конфига перед правкой подходит `sudo cp -a -- исходный-файл путь-к-уникальной-копии`. Запиши исходный путь и права. При совместной работе не перезаписывай чью-то предыдущую копию.

## 4. Сделай согласованную копию данных

| Где живут данные | Что делать |
|---|---|
| Обычные файлы в bind mount | Зафиксируй путь на хосте. Сохрани каталог, когда данные не меняются или приложение обеспечивает штатный снимок |
| Именованный том с обычными файлами | Проверь имя тома. Для статичных данных можно читать том через временный контейнер с подключением только на чтение |
| PostgreSQL | Сделай логический дамп штатной командой `pg_dump` |
| SQLite | Сделай согласованную копию через `.backup`. При WAL обычное копирование одного активного файла может дать неполные данные |
| Другой движок или внешний сервис | Используй его процедуру экспорта и уточни, какие данные и разрешения входят в копию |

### PostgreSQL

**Где:** на машине с штатным доступом к вашей учебной или игровой БД. Ниже пример с TCP к `127.0.0.1`. Если у вас Unix-сокет, контейнер или другой хост, используй параметры из инвентаря. Подставь реальную базу и выданную роль.

```bash
pg_dump -h 127.0.0.1 -p 5432 -U notes_user -d notes -Fc   -f "$backup_dir/notes-pg.dump.part" &&
  pg_restore -l "$backup_dir/notes-pg.dump.part" > /dev/null &&
  mv -- "$backup_dir/notes-pg.dump.part" "$backup_dir/notes-pg.dump"
```

`-Fc` создаёт архив в формате custom, `-f` записывает его в файл. При запросе пароля используй штатный способ аутентификации. `pg_restore -l` читает оглавление архива. Эта проверка помогает отсеять явные проблемы, а полная проверка — восстановление и чтение данных в отдельной БД. `pg_dump` сохраняет одну базу. Роли и другие объекты уровня кластера могут понадобиться отдельно. Основная версия клиента `pg_dump` должна быть не ниже основной версии сервера. [Документация pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html)

Для **репетиции на отдельном тестовом экземпляре**, если у твоей роли есть права создать пустую БД:

```bash
createdb -h 127.0.0.1 -p 55432 -U notes_test notes_restore_test &&
  pg_restore -h 127.0.0.1 -p 55432 -U notes_test -d notes_restore_test     --single-transaction --no-owner --no-acl "$backup_dir/notes-pg.dump" &&
  psql -h 127.0.0.1 -p 55432 -U notes_test -d notes_restore_test -c '\dt'
```

Порт `55432` и имя роли вымышлены. До запуска убедись, что выбрал именно свой тестовый экземпляр, который не обслуживает игровой сервис. `--single-transaction` помогает избежать частично применённого восстановления при ошибке. `--no-owner` и `--no-acl` подходят этой репетиции с отдельной ролью. Они пропускают исходных владельцев и права, поэтому полноценный план восстановления учётных записей и доступов проверяется отдельно. После списка таблиц прочитай известную учебную запись. [Документация pg_restore](https://www.postgresql.org/docs/current/app-pgrestore.html)

### SQLite

**Где:** машина, на которой виден нужный файл БД и есть `sqlite3`. Путь к БД подставь из конфигурации сервиса. В примере пути простые, без одинарных кавычек.

```bash
sqlite_source=/srv/notes/data/app.db
test -f "$sqlite_source" &&
  sqlite3 -bail "$sqlite_source" ".backup '$backup_dir/notes-sqlite.db.part'" &&
  test "$(sqlite3 -bail -readonly "$backup_dir/notes-sqlite.db.part"     'PRAGMA integrity_check;')" = ok &&
  mv -- "$backup_dir/notes-sqlite.db.part" "$backup_dir/notes-sqlite.db"
```

Первая проверка нужна, чтобы не получить пустую новую БД из-за опечатки в пути. `.backup` создаёт копию через механизмы SQLite. `integrity_check` проверяет структуру копии. При успехе ожидается `ok`. Если финальный файл не появился, проясни ошибку и не отмечай копию готовой. Проверка структуры не доказывает, что в копии есть нужные записи. Прочитай знакомую тестовую запись через отдельную копию или учебный экземпляр приложения. [Командная строка SQLite](https://www.sqlite.org/cli.html) · [PRAGMA integrity_check](https://www.sqlite.org/pragma.html#pragma_integrity_check)

### Именованный Docker-том с обычными файлами

Этот вариант подходит для **статичных файлов** в томе. Для активной БД используй её процедуру из предыдущих разделов. Пример использует уже загруженный учебный образ `alpine:3.20` с tar. Замени имя тома на фактическое из `docker inspect`.

```bash
sudo docker volume inspect notes_uploads > /dev/null &&
  sudo docker run --rm --pull=never --network none     --mount type=volume,source=notes_uploads,target=/source,readonly     alpine:3.20 tar -C /source -czf - .     > "$backup_dir/notes-uploads.tar.gz.part" &&
  gzip -t -- "$backup_dir/notes-uploads.tar.gz.part" &&
  tar -tzf "$backup_dir/notes-uploads.tar.gz.part" > /dev/null &&
  mv -- "$backup_dir/notes-uploads.tar.gz.part" "$backup_dir/notes-uploads.tar.gz"
```

`volume inspect` сверяет существование имени. `readonly` запрещает временной копировальной команде писать в том. Он не останавливает записи других контейнеров. `--pull=never` использует локальный образ, `--network none` оставляет этот контейнер без сетевого подключения, а `--rm` убирает его после завершения. Штатный том остаётся. [Резервирование томов Docker](https://docs.docker.com/engine/storage/volumes/#back-up-restore-or-migrate-data-volumes)

## 5. Скачай копию и проверь её

Ниже формируем ведомость хешей на vulnbox из **конкретных готовых файлов**. Если у твоего сервиса PostgreSQL вместо SQLite, подставь имя созданного дампа.

```bash
(
  cd "$backup_dir" &&
    sha256sum -- notes-files.tar.gz notes-sqlite.db > SHA256SUMS.part &&
    mv -- SHA256SUMS.part SHA256SUMS
)
```

Теперь в **терминале на рабочем ПК** подставь адрес, SSH-порт, логин и реальное имя каталога `notes-ABC123` из шага 2:

```bash
umask 077
mkdir -p "$HOME/innoctf/backups"
download_dir=$(mktemp -d "$HOME/innoctf/backups/notes-XXXXXX")
test -n "$download_dir" &&
  scp -r -P 22 player@10.2.17.2:ad-backup/notes-ABC123 "$download_dir/" &&
  (cd "$download_dir/notes-ABC123" && sha256sum -c SHA256SUMS)
```

`-r` нужен для каталога, `-P` задаёт SSH-порт. Если используешь ключ с нестандартным именем, добавь `-i "$HOME/.ssh/innoctf_ed25519"`. Сохрани закрытый каталог на своём ПК. Проверь, что перечисленные файлы получили `OK`, а каталог содержит именно комплект нужного сервиса. `.part` — остатки незавершённых попыток, их не используй для восстановления. Совпадение хеша в этом сценарии проверяет целостность передачи.

## 6. Как выбирать откат в матче

| Что сломалось | С чего начать |
|---|---|
| Ошибка после правки одного конфига | Вернуть прежний файл, проверить синтаксис, перечитать или применить настройки штатно |
| После перезапуска видны только новые записи | Сверить путь к БД или имя тома с исходным инвентарём. Старая база может быть целой |
| Заменён код, конфиг и данные на месте | Восстановить известную версию кода и исполнить тот же штатный сценарий |
| Подтверждена порча или утрата БД | Сначала сохранить текущее состояние отдельно. Проверить копию на отдельном экземпляре, затем согласовать переключение |
| Архив читается, а сервис после восстановления не стартует | Проверить владельцев файлов, формат и версию БД, переменные и зависимости |

После восстановления проверь **старую тестовую запись, новую запись и повторный вход** через рабочую сеть. Сверь следующий результат Jury, если игра уже идёт. Возврат старой БД может потерять всё, что записано после точки копирования. Когда старая база цела, предпочтительнее восстановить подключение к ней.

## 7. Мини-тренировка

1. Создай в учебном сервисе заметку «до копии».
2. Сделай копию приложения и данных, затем скачай её и сверь хеши.
3. Открой данные в отдельной папке или отдельной БД. Проверь, что заметка «до копии» читается.
4. Вернись к исходному учебному сервису и создай заметку «после копии».
5. Сравни исходный сервис и восстановленную копию. Вторая заметка должна быть в исходном сервисе, но её ещё нет в старой копии. Запиши, какие записи потерялись бы при полном откате к этому моменту.
