# 10. Защитное ревью кода сервиса

[Оглавление](./README.md) · [Как читать сервис](./09-read-a-service.md) · [Атакующая сторона в механике игры](./11-attack-side-concepts.md)

В главе 09 мы нашли обработчик `GET /notes/:id` и поняли, где он берёт данные. Теперь сформулируем, **что этот обработчик обязан гарантировать**: читать личную заметку может её владелец, а после исправления он всё ещё видит свои старые записи. На соревновании нужно проверить обе половины этого правила.

Примеры ниже относятся к вымышленным «Заметкам». Команды и тестовые примеры предназначены для своего кода и изолированной учебной среды.

## 1. Перед ревью выпиши ожидаемое поведение

| Кто и что делает | Ожидаемый результат в учебном сервисе | Зачем это нужно |
|---|---|---|
| Алиса входит и открывает свою старую заметку | Страница показывает правильный текст | Проверяет сохранение доступа и старых данных |
| Алиса создаёт новую заметку | После сохранения она читается | Проверяет обычный сценарий записи |
| Борис обращается к приватной заметке Алисы | Отказ, содержимое не возвращается | Проверяет правило доступа к объекту |
| Пользователь без входа запрашивает приватную заметку | Отказ или предусмотренный редирект на вход | Проверяет, что требуется аутентификация |
| Владелец открывает запись, которой нет | Штатный ответ приложения, например `404` | Проверяет обработку отсутствующих данных |

Если у задачи бывают общие заметки, роли редактора или ссылки «просмотр по приглашению», добавь их в таблицу сразу. Защитная правка должна сохранить эти разрешённые сценарии. Код ответа тоже часть контракта, если от него зависит клиент или чекер.

## 2. Где начинается проверка прав

**Аутентификация** устанавливает, кто вошёл. **Авторизация** отвечает, разрешено ли этому пользователю конкретное действие над конкретной записью. Успешный вход сам по себе не даёт доступ ко всем объектам. Проверка должна выполняться на сервере для каждой защищённой операции. [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

Возьми карту главы 09 и для одного обработчика выпиши:

1. **Откуда берётся пользователь.** В учебном сервисе это сервером проверенная сессия. Личность не принимают из произвольного поля запроса.
2. **Что защищаем.** Идентификатор записи пришёл из маршрута. Само число — указатель на объект, а право определяется отдельно.
3. **Где правило гарантировано.** В «Заметках» владелец входит в условие выборки. В другой архитектуре это может быть отдельная политика доступа.
4. **Что возвращаем при отказе.** Пример использует одинаковый публичный результат для отсутствующей и недоступной записи. Сохраняй контракт реального сервиса.
5. **Где правило повторяется.** Если сервис умеет редактировать, удалять и экспортировать запись, у этих операций должны быть свои проверки. Исправление одного чтения не меняет остальной код.

### Учебный пример для слоя данных

Этот фрагмент работает с уже открытым соединением SQLite. `viewer_id` должен прийти из доверенной логики сессии, а `note_id` — из проверенных параметров запроса.

```python
def find_private_note(db, note_id, viewer_id):
    return db.execute(
        "SELECT id, title, body FROM notes WHERE id = ? AND owner_id = ?",
        (note_id, viewer_id),
    ).fetchone()
```

Здесь две разные гарантии. `owner_id = ?` ограничивает выборку владельцем. Отдельная передача значений в `db.execute` даёт драйверу связать параметры как данные. Синтаксис параметров зависит от драйвера. В `sqlite3` можно использовать `?`, а в другом драйвере нужно сверить его документацию. [OWASP SQL Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)

Проверку репозитория удобно выполнить без сети на временной БД. Ниже иллюстрация для таблицы, где заметка №42 принадлежит Алисе с ID 7, а Борис имеет ID 8:

```python
assert find_private_note(db, 42, 7) == (42, "Моя заметка", "Старый текст")
assert find_private_note(db, 42, 8) is None
assert find_private_note(db, 999, 7) is None
```

Это тест учебных записей, которые ты сам создал. Отдельный тест обработчика проверяет, как результат `None` превращается в ожидаемый HTTP-ответ. Один тест функции БД ещё не доказывает, что к ней ведут все нужные маршруты.

## 3. Проверка входных данных

Когда читаешь обработчик, пометь каждое значение, которое пришло от клиента: поля JSON, параметры пути, выбор сортировки и файл. У каждого значения должен быть понятный допустимый тип и смысл.

| Поле | Что проверить в «Заметках» | Как проверить исправление |
|---|---|---|
| Заголовок | Строка, не пустая после проверки пробельных символов. Длина в рамках контракта | Обычная строка проходит. Пустая и слишком длинная получают штатный отказ |
| Текст | Строка подходящего размера. Обычная пунктуация и русский текст сохраняются | Прочитать обратно текст с кавычками и переносом строки |
| Сортировка | Выбор одного из предусмотренных вариантов | Два поддерживаемых режима работают, неизвестный обрабатывается штатно |
| Путь к вложению | Приложение хранит и проверяет принадлежность вложения по своим правилам | Владелец открывает своё тестовое вложение, недоступное не выдаётся |

Простой пример проверки заголовка. Лимит 80 символов условный. Перед переносом в игровую задачу проверь реальный контракт, иначе можно случайно сломать существующий сценарий.

```python
def valid_title(value):
    return isinstance(value, str) and bool(value.strip()) and len(value) <= 80
```

Проверка формата помогает приложению обработать нормальные и ошибочные данные. Она не заменяет авторизацию, параметризацию SQL и штатное экранирование при выводе в HTML. Если настройка допускает несколько типов сортировки, сопоставь известный вариант с фиксированным значением в коде. [OWASP Input Validation Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html)

## 4. Отладка, секреты и полномочия

| Что заметил в своём сервисе | Как проверить и исправить | Что должно сохраниться |
|---|---|---|
| В игровом ответе виден traceback | Открой настройки запуска. Отключи внешний отладчик и подробные страницы ошибок по документации фреймворка | Клиент получает предусмотренный краткий ответ, детали есть в разрешённом серверном журнале |
| В конфиге виден пароль или токен | Установи, кто имеет доступ к файлу и где значение используется. Убери секрет из публичного кода или вывода, при подтверждённой утечке согласуй замену | Сервис, база и чекер продолжают работать с предусмотренной конфигурацией |
| В журнал пишется весь запрос или содержимое записи | Оставь время, маршрут, код результата, безопасный идентификатор запроса и нужное событие. Проверь маскирование чувствительных полей | Инцидент можно связать со временем и маршрутом без копирования паролей, токенов, cookie и флагов |
| Приложение запущено под избыточной ролью | Выпиши нужные операции. Согласуй меньшие права для запуска, БД или файлов, затем повтори обычные проверки | Читаются старые данные, создаются новые, штатные зависимости доступны |

Смену ключа сессий или пароля БД рассматривай как отдельное изменение. Оно может завершить старые сеансы или временно лишить доступа приложение. Если подозреваешь утечку, запиши, какие части системы придётся переключить и как проверить результат.

У Flask встроенный отладчик рассчитан на разработку. В игровом запуске важны серверные логи с достаточным контекстом и штатный ответ клиента без внутренних деталей. [Отладка Flask](https://flask.palletsprojects.com/en/stable/debugging/) · [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

## 5. Как выбрать первую небольшую правку

1. **Опиши правило одной фразой.** Например: «Читать личную заметку может владелец».
2. **Зафиксируй исходное поведение** на двух своих учебных учётках и одной старой записи. Запиши время, результат и работающий штатный сценарий.
3. **Сохрани исходный файл и нужные данные.** Запиши, как его вернуть. Если важно состояние базы, сначала прочитай [главу 08](./08-backup-and-restore.md).
4. **Поправь один слой**, где правило должно применяться. Прочитай изменение построчно.
5. **Проверь положительный и отрицательный случаи на своих данных.** Для владельца заметка открывается. Для пользователя без права содержимое не выдаётся.
6. **После применения проверь старые и новые записи с ПК**, затем следующий статус Jury. Если обычный сценарий перестал работать, верни понятное последнее изменение и проверь снова.

Запись для команды:

> «Заметки», 11:10. В учебной копии проверил правило чтения личной записи. По коду ограничили выборку владельцем. Алиса читает старую запись, Борис получает штатный отказ. Версия до правки сохранена. На игровой машине повторяем обычный сценарий после применения, затем сверяем Jury.

## 6. Вопросы для самопроверки

1. В приложении скрыта кнопка удаления, если заметка не твоя. Где всё равно нужна проверка?
2. Запрос к БД параметризован. Даёт ли это гарантию, что запись принадлежит текущему пользователю?
3. Патч проходит тест отказа, но владелец перестал видеть свою заметку. Можно ли считать правку готовой?
4. Чекер краснеет после смены роли БД, хотя главная страница открывается. Какой следующий тест?
5. Какие сведения полезно оставить в логе для диагностики и каких полей там быть не должно?

<details>
<summary>Ответы</summary>

1. На сервере в операции удаления или общей политике доступа, которую она вызывает.
2. Нет. Параметризация управляет тем, как синтаксис SQL отделён от данных. Правило владения проверяется отдельно.
3. Нет. Нужно сохранить штатную операцию владельца и старые записи.
4. Выполнить штатные операции чтения и записи, сверить результат с привилегиями роли и логами за время теста.
5. Время, маршрут, код результата, идентификатор запроса и тип события. Пароли, токены и содержимое флагов в такой записи лишние.

</details>
