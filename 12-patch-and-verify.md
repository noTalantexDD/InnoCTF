# 12. Правка сервиса, проверка и откат

[Оглавление](./README.md) · [Защитное ревью кода](./10-defensive-code-review.md) · [Логи и трафик](./13-logs-and-traffic.md)

Команда исправила проверку прав в «Заметках». После выкладки сервис отвечает на HTTP, но владелец больше не может открыть свою старую запись. Чтобы сразу понять, где сломалось, до изменения нужны исходный тест, копия конкретного файла и ответственный за откат.

Рабочий порядок: **проверить до → сохранить → изменить одну вещь → проверить в учебной копии → применить → повторить тот же тест → сверить Jury**. Ниже есть пример для своего сервиса под systemd и развилка для Docker.

## 1. Зафиксируй исходный сценарий

Возьми карточку сервиса из [главы 07](./07-service-inventory.md). С рабочего ПК проверь несколько действий. По возможности используй тестовые учётки и записи, принадлежащие вашей команде.

| Что проверяем | Ожидаемый пример | Что запомнить |
|---|---|---|
| HTTP доступен | На штатном маршруте отвечает ваше приложение | URL, время, код и простой признак правильного ответа |
| Старые данные | Алиса читает свою заметку, созданную до правки | ID учебной записи и факт, что ожидаемый текст читается |
| Новая запись | Алиса создаёт и открывает новую заметку | В каком шаге возможна ошибка: создать, сохранить или прочитать |
| Правило доступа | Вторая учебная учётка получает предусмотренный отказ при обращении к закрытой учебной записи | Как выглядит штатный отказ и какие разрешённые роли нужно сохранить |
| Судейский статус | Последний видимый тик и код | После правки сравнишь его со свежей проверкой, если она появится |

Если штатная операция уже не работала, запиши это до редактирования. Тогда следующий сбой можно сравнить с исходным состоянием. Код `200` на главной подтверждает только ответ на этот путь.

Короткий замер HTTP для **своего** сервиса, если у него предусмотрен маршрут `/health`. Подставь выданное значение и реальный путь. **Где:** рабочий ПК.

```bash
curl --noproxy '*' -sS -o /dev/null \
  -w 'http=%{http_code} time=%{time_total}s\n' \
  --connect-timeout 4 --max-time 8 "http://10.2.17.2:8080/health"
```

`-o /dev/null` для этого теста убирает тело. `-w` показывает код и длительность. `http=000` при ошибке соединения означает, что HTTP-ответ не получен или не прочитан применительно к этому вызову. Если проверяешь правильность содержимого ответа, не отбрасывай тело. [Справка curl](https://curl.se/docs/manpage.html)

## 2. Согласуй изменение и сделай обратимую копию

Перед началом ответь напарнику на три вопроса: **где меняю, что должно измениться, как верну рабочее состояние**. Если изменяемый файл общий для нескольких процессов, сначала договорись с их владельцами. Не меняй конфиг, код и базу одним шагом.

Для примера «Заметки» работают под systemd как `notes.service`. Файл `/opt/notes/app/access.py` — обычный файл в каталоге сервиса, не симлинк. Ты уже проверил, что именно эту версию загружает процесс. Если в вашем сервисе код упакован в образ или путь является ссылкой, сначала выясни способ выкладки.

**Где:** SSH на своём vulnbox. В этом примере учётка имеет выданные права `sudo`.

```bash
umask 077
mkdir -p -m 700 "$HOME/ad-backup"
patch_backup=$(mktemp -d "$HOME/ad-backup/notes-patch-XXXXXX")
patch_file=/opt/notes/app/access.py
test -n "$patch_backup" && sudo cp -a -- "$patch_file" "$patch_backup/access.py" &&
  printf 'source=%s\nbackup=%s\n' "$patch_file" "$patch_backup/access.py"
```

`mktemp` создаёт уникальную папку. `cp -a` сохраняет копию с атрибутами. В журнале записывай полный путь копии, который напечатала последняя строка, и время. Переменные будут доступны в этой вкладке SSH. При новом входе подставь точные сохранённые пути. Если копия не появилась или путь не тот, сначала разберись с этим.

Если собираешься менять хранилище, простой копии кода мало. Подготовь отдельный бэкап данных и проверь его по [главе 08](./08-backup-and-restore.md).

## 3. Сделай один патч и проверь его отдельно

В примере исправляется правило чтения личной заметки в существующем слое доступа. Оно должно опираться на текущую учётку и владельца записи. Дополнительные роли и предусмотренный общий доступ сохраняются, если они есть в реальном контракте.

1. В учебной копии внеси правку в один участок и просмотри изменения. Если проект в Git, помогает `git diff -- app/access.py`. Команда чтения показывает отличия от индекса, а для уже подготовленной к коммиту правки нужен `git diff --cached -- app/access.py`.
2. Запусти штатные тесты проекта на разрешённых учебных данных. Проверь чтение старой записи владельцем и штатный отказ для второй тестовой учётки. Затем проверь создание новой записи.
3. Если файла с тестами пока нет, хотя бы запиши результаты этих действий и укажи, какая часть проверялась вручную.
4. После переноса выбранной правки проверь конфиг или синтаксис до применения. Штатная команда проекта имеет приоритет.

Быстрая проверка синтаксиса обычного Python-файла, **если это действительно Python**. Этот пример читает файл без импорта приложения и без создания `__pycache__`:

```bash
python3 - "$patch_file" <<'PY'
import ast
import sys
import tokenize

with tokenize.open(sys.argv[1]) as source:
    ast.parse(source.read(), filename=sys.argv[1])
print("Syntax OK")
PY
```

Версия Python для проверки должна подходить к версии процесса. Если получен `SyntaxError`, остановись и исправь файл или верни копию. «Syntax OK» подтверждает возможность разобрать код. Тесты и пробный запуск проверяют зависимости и поведение отдельно.

## 4. Примени изменение подходящим способом

| Что поменялось | Типичный способ применения | Что сверить до команды |
|---|---|---|
| Конфиг приложения с поддержкой перечитывания | Его штатный `reload` | Каким синтаксическим тестом проверяют именно этот конфиг |
| Код, который процесс загрузил при старте | Точечный перезапуск процесса по инструкции сервиса | Точное имя службы, ожидаемая недоступность, бэкап и перезапуск нужной версии |
| Юнит systemd или drop-in | `systemctl daemon-reload`, затем действие над самим сервисом | `daemon-reload` перечитывает определения systemd. Для запуска сервиса с новой конфигурацией может потребоваться отдельный перезапуск |
| Файл, смонтированный в контейнер | Перечитывание или перезапуск только нужного сервиса | Файл действительно виден приложению по нужному пути |
| Настройки `compose.yaml`, переменные или образ | Штатное пересоздание конкретного контейнера по проекту | Реальные Compose-файлы, зависимости, образ, тома и способ возврата |
| Миграция БД | Процедура проекта с проверенным планом отката данных | Совместимость кода и схемы, разделение новых и старых записей, время и проверенная копия |

### Учебный пример с systemd

В примере вы подтвердили `notes.service`, код загружается при старте, а площадка допускает точечный перезапуск. **Где:** свой vulnbox.

```bash
sudo systemctl restart notes.service &&
  systemctl is-active notes.service
sudo journalctl -u notes.service --since "2 minutes ago" -n 40 --no-pager
```

`active` означает, что systemd считает службу запущенной. Проверка приложения с ПК остаётся отдельной. Если изменялась служба SSH, используй [порядок из главы 06](./06-ssh-and-hardening.md) с резервным открытым сеансом. [Документация systemctl](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html)

### Если сервис в Compose

Сначала из рабочего каталога **правильного проекта** проверь имена и состояние:

```bash
sudo docker compose config --quiet
sudo docker compose ps --all
```

`config --quiet` проверяет конфигурацию проекта. `ps --all` покажет и остановленные контейнеры. Простой `docker compose restart` не применит новые настройки из Compose-файла к уже созданному контейнеру. Сначала установи, что менялось: смонтированный файл, параметры контейнера, образ или данные. При пересоздании следуй выданной команде проекта с нужными файлами и именем сервиса. Согласуй, будут ли тронуты зависимости и какой образ необходим. Проверка томов — часть плана перед пересозданием. [Docker Compose restart](https://docs.docker.com/reference/cli/docker/compose/restart/) · [Docker Compose up](https://docs.docker.com/reference/cli/docker/compose/up/)

## 5. Проверь после применения и реши, нужен ли откат

**С ПК** повтори те же операции, что были в исходном тесте. Если начинает работать `/health`, продолжи до чтения старой записи, создания новой и проверки отказа на учебной учётке. Запиши время, затем сверяйся со свежим тиком. Старый красный статус до следующей проверки может оставаться видимым.

| Наблюдение | Действие |
|---|---|
| Новый процесс не запустился | Сохрани относящиеся к моменту сбоя строки лога. Верни изменённый код или конфиг и повтори применение |
| Процесс запущен, но обычный пользовательский сценарий перестал работать | Зафиксируй сломанный шаг и верни последнее известное изменение. Повтори исходную проверку |
| Новые записи работают, а старая отсутствует | Проверь настройку подключения и том до попытки восстановить данные |
| Локальная проверка прошла, обновления Jury ещё нет | Запиши свой результат и время. Следующую проверку оцени отдельно |
| Чекер часто краснеет после одной правки, но причины ещё не видно | Сверь время на сервере и табло, проверь логи и воспроизводимый штатный сценарий |

Откат примера, где менялся **только** `access.py`. **Где:** терминал vulnbox, переменные должны содержать те же проверенные пути. Если другой участник успел изменить файл, сначала согласуйте, какую версию вернуть.

```bash
test -n "$patch_backup" && test -n "$patch_file" &&
  sudo test -f "$patch_backup/access.py" &&
  sudo cp -a -- "$patch_backup/access.py" "$patch_file" &&
  sudo systemctl restart notes.service &&
  systemctl is-active notes.service
```

Затем повтори тест с ПК. Если затронуты привязка БД и данные, остановись на диагностике из главы 08. Восстановление старого дампа может убрать записи, появившиеся после момента копирования.

## 7. Самопроверка

1. Как понять, что возврат нужен только для одного файла?
2. Почему `docker compose restart` может оставить старые переменные контейнера?
3. Какими тестами отличить исчезновение данных от поломки сохранения новых записей?
4. Кто и когда должен записать решение об откате в журнал?

<details>
<summary>Ответы</summary>

1. До и после зафиксировано, что менялся именно этот файл. Данные и конфигурация запуска остались прежними, а наблюдаемый сбой соответствует правке.
2. Перезапуск работает с тем же созданным контейнером. Новое описание проекта требует соответствующей операции применения.
3. Сравнить чтение записи, созданной до изменения, и запись с последующим чтением новой.
4. Ответственный за правку или согласованный владелец сервиса. Он записывает время, симптомы, сохранённый путь и результат повторного теста сразу после действия.
