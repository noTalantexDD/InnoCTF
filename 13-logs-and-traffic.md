# 13. Логи и сетевой трафик на A/D

[Оглавление](./README.md) · [Инвентарь сервисов](./07-service-inventory.md) · [Правка и откат](./12-patch-and-verify.md)

Чекер показал `MUMBLE`, а приложение открывается в браузере. Твой первый вопрос: **до какого слоя дошла именно та операция, которая не сработала?** Сетевой захват помогает увидеть обмен пакетами. Лог прокси показывает, куда ушёл запрос и чем он закончился. Лог приложения объясняет, что произошло внутри. Для диагноза обычно хватает одного узкого интервала и одного воспроизводимого теста.

Все примеры чтения и захвата относятся к своему приложению, своей машине и учебному клиенту в пределах правил площадки.

## 1. Выбери источник по вопросу

| Вопрос | Источник | Что можно увидеть |
|---|---|---|
| Дошёл ли TCP-запрос до интерфейса? | `tcpdump` на подходящем интерфейсе | Адреса, порты, время, флаги TCP, размеры |
| Принял ли веб-сервер запрос? | Access log или лог обратного прокси | Маршрут, код, время и ID запроса, если это настроено |
| Почему операция завершилась ошибкой? | Лог приложения или systemd | Ошибка кода, недоступная БД, некорректная конфигурация |
| Что увидел сервер БД? | Штатный журнал БД при доступе команды | Ошибка подключения, недоступная таблица или отклонённая операция |
| Что успел проверить судья? | Jury и [статус чекера](./02-flags-and-scoreboard.md) | Тик, конкретный сервис и видимый результат |

У одного сервиса может быть больше одного источника. Например, nginx проксирует запрос в контейнер `notes-web`, а чтение зависит от отдельной БД. Пустой лог бывает следствием неправильного имени контейнера, часового пояса, слишком узкого окна или настроек журнала.

## 2. Сначала договорись о времени

1. Запиши время статуса в Jury вместе с тиком и часовым поясом интерфейса.
2. Перед своим тестом посмотри время на ПК и сервере: `date -Is` покажет локальный сдвиг, `date -u -Is` — время в UTC.
3. Сделай один обычный запрос, результат которого можно повторить. Запиши время на ПК и примерный интервал на сервере.
4. Ищи рядом с этим временем, учитывая разницу часов и задержку обновления табло. Начни с 10–30 секунд вокруг теста, если часы согласованы. Увеличь окно, если статус известен только с точностью до раунда.
5. Если приложение имеет ID запроса, сверяй и его. Когда ID нет, совпадение времени и пути остаётся гипотезой, особенно при параллельных запросах.

Далее в примерах 21 ноября 2026 года и `08:10 UTC` — учебные отметки. Замени их временем своей проверки.

## 3. Найди нужные строки без пролистывания всего журнала

### Вариант systemd

**Где:** своё приложение на vulnbox. `notes.service` — учебное имя юнита.

```bash
sudo journalctl -u notes.service \
  --since "2026-11-21 08:09:50 UTC" \
  --until "2026-11-21 08:10:20 UTC" \
  --utc -o short-iso-precise --no-pager
```

`-u` выбирает юнит. `--since` и `--until` ограничивают окно. `--utc` делает отображение времени сопоставимым с другими журналами, а `short-iso-precise` добавляет точность. Если знаешь только, что ошибка произошла только что, можно начать с `--since "2 minutes ago" -n 50`. [Документация journalctl](https://www.freedesktop.org/software/systemd/man/latest/journalctl.html)

### Вариант Docker

**Где:** свой vulnbox с выданным доступом к Docker. `notes-web` — учебное имя контейнера.

```bash
sudo docker logs --timestamps \
  --since "2026-11-21T08:09:50Z" \
  --until "2026-11-21T08:10:20Z" \
  --tail 100 notes-web
```

Буква `Z` означает UTC. `--timestamps` печатает время, `--tail 100` ограничивает объём. Этот способ полезен, если процесс пишет в потоки, которые доступны через логи Docker. Если контейнер пересоздавался, проверь, у какого экземпляра были нужные события и сохранились ли его логи. [Документация docker logs](https://docs.docker.com/reference/cli/docker/container/logs/)

Для файлового лога сначала узнай реальный путь из выданной конфигурации сервера. У привычного `/var/log/nginx/access.log` может быть другой путь. Бери только строки нужного интервала. В общем чате хватит времени, пути без чувствительных параметров, ID запроса, кода и обезличенной ошибки. Пароли, cookie и тело запроса могут попасть даже в журналы отладки.

## 4. Что такое PCAP и зачем TCP-флаги

**PCAP** — файл с сохранёнными пакетами. Захват можно посмотреть позже в tcpdump или Wireshark. При обычном HTTPS содержимое HTTP защищено TLS. Сетевой захват всё равно может показать, был ли TCP-обмен и как долго он продолжался. Об ошибке внутри приложения лучше узнать из его журнала.

| Что видно в учебном TCP-обмене | Что можно предположить |
|---|---|
| Клиент отправляет `SYN`, сервер отвечает `SYN, ACK`, клиент подтверждает `ACK` | Трёхстороннее установление TCP прошло |
| Видны повторяющиеся `SYN` без ответа в выбранной точке | Есть проблема пути, фильтра или ответа. Сначала сверь интерфейс и направление захвата |
| После попытки сразу виден `RST` | Соединение активно отклонено или сброшено. Проверь кто прислал RST, слушает ли порт и что делают правила сети |
| TCP установился, а HTTP вернул `500` | Сеть для этого запроса сработала. Переходи к прокси, приложению и зависимостям |

### Короткий просмотр своих пакетов на vulnbox

Только если это разрешено площадкой. Пример ограничен **одним учебным ПК команды** и известным сервисом. Замени интерфейс `eth0`, адрес `10.2.17.23` и порт `8080` реальными значениями. **Где:** свой vulnbox. После запуска сделай один обычный запрос из указанного ПК.

```bash
sudo timeout --signal=INT 15s tcpdump -nn -i eth0 -c 20 \
  'host 10.2.17.23 and tcp port 8080'
```

`-i` выбирает интерфейс, `-nn` сохраняет числовые адреса и порты, `-c 20` останавливает просмотр после 20 пакетов. `timeout` ограничивает время. Если он завершает просмотр по лимиту, возможен код возврата 124. Эта команда печатает сводку без явного вывода содержимого и без записи PCAP. Пустой захват ещё не доказывает, что запрос не дошёл: сеть может менять адрес источника или вести пакеты через другой интерфейс. Начни с [маршрута и порта](./05-network-and-proxy.md). [Руководство tcpdump](https://www.tcpdump.org/manpages/tcpdump.1.html)

## 5. Как потренироваться на своём ПК и получить учебный PCAP

Для тренировки воспользуйся loopback `127.0.0.1`. Этот пример запускает отдельный учебный HTTP-сервер без паролей и реальных данных.

**Локальный терминал A:**

```bash
lab_web=$(mktemp -d)
test -n "$lab_web" && printf 'demo response\n' > "$lab_web/index.html" &&
  python3 -m http.server 18080 --bind 127.0.0.1 --directory "$lab_web"
```

Если всё запустилось, терминал остаётся занят. Если порт уже занят, выбери другой и подставь его во все команды примера.

**Локальный терминал B:** начни захват на Linux или WSL там же, где работает сервер. Потребуется разрешение на захват. Сохрани тест в закрытый каталог:

```bash
umask 077
capture_dir=$(mktemp -d)
printf '%s\n' "$capture_dir"
test -n "$capture_dir" &&
  sudo timeout --signal=INT 12s tcpdump -i lo -s 0 -U -w - \
    'host 127.0.0.1 and tcp port 18080' > "$capture_dir/notes-demo.pcap"
```

`-w -` пишет захват в стандартный вывод. Перенаправление сохраняет его как файл текущего пользователя. `-U` выводит пакеты по мере записи, `-s 0` позволяет сохранить содержимое учебного обмена. При таком захвате нельзя отправлять в этот тест реальные учётные данные, токены или флаги.

**Локальный терминал C:** пока захват идёт, сделай запрос:

```bash
curl --noproxy '*' -sS -i --max-time 4 http://127.0.0.1:18080/
```

Ожидается ответ `200` и `demo response`. Когда захват завершится, в B выполни `tcpdump -nn -tttt -r "$capture_dir/notes-demo.pcap"`. `-r` читает файл без нового захвата, `-tttt` выводит полную дату и время. В A можно остановить учебный сервер через Ctrl+C. Использовать этот шаг на настоящей игровой сети стоит только в рамках правил и узкого диагностического вопроса.

## 6. Suricata, IDS, IPS и EVE JSON

| Термин | Что значит |
|---|---|
| **IDS** | Обнаруживает события и может записывать предупреждения, исходя из правил и наблюдаемого трафика |
| **IPS** | Может блокировать трафик, если установлен в путь пакетов и настроен соответствующим образом |
| **Suricata** | Анализатор, поддерживающий оба режима и разбор сохранённых захватов |
| **EVE JSON** | Поток записей JSON. В зависимости от настроек там могут быть `alert`, `flow` и протокольные события |
| **Алерт** | Сработавшее правило. Он говорит о совпадении с условием, а последствия проверяются отдельно |

Для первого знакомства можно открыть **учебный PCAP** офлайн. Если Suricata установлена, правила и EVE включены в твоём тестовом конфиге, используй отдельный каталог для вывода. `/etc/suricata/suricata.yaml` — пример пути. Передай Suricata отдельную копию захвата. Тогда настройки обработки PCAP не затронут исходный файл.

```bash
suricata_out=$(mktemp -d)
test -n "$suricata_out" &&
  cp -- "$capture_dir/notes-demo.pcap" "$suricata_out/input.pcap" &&
  suricata -c /etc/suricata/suricata.yaml \
    -r "$suricata_out/input.pcap" -l "$suricata_out"
```

`-r` читает запись офлайн, `-l` задаёт каталог вывода. При наличии `eve.json` можно выбрать поля алертов, если установлен jq:

```bash
jq -c 'select(.event_type == "alert") |
  {timestamp, src_ip, dest_ip, dest_port, signature: .alert.signature}' \
  "$suricata_out/eve.json"
```

Для обычного учебного `GET` вполне ожидаемо не увидеть алертов. Проверь, что был загружен набор правил и создался журнал. Отсутствие совпадений зависит от правил, настройки и видимости трафика. Если EVE не появился, сначала смотри сообщения запуска и конфигурацию вывода. Работа офлайн подходит для изучения событий без изменения сетевого пути сервиса. [Suricata CLI](https://docs.suricata.io/en/latest/command-line-options.html) · [EVE JSON](https://docs.suricata.io/en/latest/output/eve/eve-json-output.html)

## 7. Разбор одного красного тика

Учебный пример. Для запроса команды его ID появился в прокси и приложении. ID судейского запроса команда не видела.

| Время UTC | Источник | Что наблюдаем |
|---|---|---|
| 08:10:05 | Jury | У «Заметок» `MUMBLE`. Точный судейский запрос не показан |
| 08:10:12.105 | Клиент команды | Начали открывать старую учебную заметку |
| 08:10:12.108 | Прокси | Запрос `demo-17` к «Заметкам» дошёл до прокси. Ответ ожидался от приложения |
| 08:10:12.109 | Служба приложения | Ошибка чтения из БД перед завершением рабочего процесса. В логе тот же ID `demo-17` |
| 08:10:12.110 | Клиент команды | Открыть заметку не удалось. Получен HTTP `502` |
| 08:10:40 | Клиент команды | После восстановления подключения старая запись читается. Новый статус Jury ещё не показан |

Для повторённого теста логи связываются по ID. Из него видно, что клиентский запрос дошёл до приложения, а ошибка возникла при чтении данных. Это объясняет тест команды. Совпадение с `MUMBLE` даёт гипотезу о судейском сбое. Чтобы проверить, ушла ли проблема у Jury, нужно следующее наблюдение.

## 8. Самопроверка

1. Захват показал полный TCP-handshake. Где дальше искать причину `500`?
2. В логах адрес шлюза повторяется у многих запросов. Доказывает ли это, что всё отправил один игрок?
3. В EVE есть алерт. Почему нужен лог приложения?
4. Учебная операция после правки прошла, а статус Jury ещё старый. Что написать команде?

<details>
<summary>Ответы</summary>

1. В логе прокси, обработчике приложения и состоянии зависимости, к которой он обращался.
2. Нет. Маршрутизация и преобразование адресов могут менять видимый источник.
3. Алерт обозначает событие по правилу. Чтобы понять итог для сервиса, нужно сопоставить время, запрос и наблюдаемое поведение приложения.
4. Указать время и результат штатного теста, отдельно записать последний видимый тик и дождаться новой проверки.
