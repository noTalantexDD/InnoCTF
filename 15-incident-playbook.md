# 15. Аварийные сценарии на A/D

[Оглавление](./README.md) · [Что делать по ходу матча](./14-match-playbook.md) · [Логи и трафик](./13-logs-and-traffic.md)

Эта глава нужна, когда что-то уже сломалось. Найди симптом в таблице и выполни **три первые проверки**. Потом выбирай откат и подтверждай результат тем же действием, которое не проходило раньше.

Команды предназначены для своего vulnbox и рабочих ПК команды. В примерах `10.2.17.2` — условный адрес сервера, `player` — логин, `22` — SSH-порт, `8080` — порт учебных «Заметок». Подставь свои значения. Имена `notes.service`, `notes-web` и пути ниже вымышлены.

## 1. Зафиксируй симптом

| Что видишь | Куда идти |
|---|---|
| Новый SSH-вход не открывается | [SSH недоступен](#2-ssh-недоступен) |
| Контейнер перезапускается или сразу завершается | [Контейнер не держится](#3-контейнер-не-держится) |
| Приложение отвечает на сервере, но с рабочего ПК нет | [Сервис отвечает только локально](#4-сервис-отвечает-только-локально) |
| HTTP отвечает, а Jury красный | [HTTP отвечает, Jury красный](#5-http-отвечает-jury-красный) |
| Новая запись появляется, старые пропали | [Пропали старые данные](#6-пропали-старые-данные) |
| Запись падает с `No space left on device` | [Закончилось место](#7-закончилось-место) |

Сразу выпиши **время и часовой пояс, сервис, последний тик и последнее изменение**. Уточни масштаб: один сервис, несколько или весь сервер. Если один участник уже трогает общий конфиг, передай ему наблюдение и согласуй следующие действия.

## 2. SSH недоступен

**Первые три проверки**

1. **На ПК:** проверь адрес и порт из выдачи. Попроси напарника с разрешённым доступом проверить тот же адрес. Если Linux или WSL, посмотри выбор маршрута через `ip route get 10.2.17.2`.
2. **На ПК:** запусти одно новое соединение, чтобы отделить проблему сети от аутентификации. Впиши свой ключ вместо учебного.
3. **В старом SSH-сеансе или через консоль:** проверь слушающий порт, состояние службы и последние сообщения.

```bash
# Рабочий ПК
ssh -p 22 -i "$HOME/.ssh/innoctf_ed25519" -o IdentitiesOnly=yes -o ControlPath=none -o ConnectTimeout=5 player@10.2.17.2
```

```bash
# Свой vulnbox, старый сеанс или консоль
sudo ss -lntp 'sport = :22'
systemctl status ssh --no-pager
sudo journalctl -u ssh --since "5 minutes ago" -n 40 --no-pager
```

Если юнит называется `sshd`, подставь его. `Connection timed out` указывает, что подключение не установилось в срок. `Connection refused` — активный отказ, например при отсутствии слушающего сокета. `Permission denied (publickey)` обычно означает, что удалённый SSH ответил, а отказ получен на этапе входа. При смене отпечатка хоста проверь выдачу и доверенную консоль до любых изменений `known_hosts`.

**Откат.** Если проблема началась после правки SSH, из запасного сеанса или консоли верни изменённый конфиг и включаемые фрагменты, либо убери новый фрагмент из пути `Include`. Сначала `sudo sshd -t`, затем перечитай рабочий юнит по порядку из [главы 06](./06-ssh-and-hardening.md). Если резервного доступа нет, обращайся к жюри.

**Критерий восстановления.** Новый SSH-сеанс открывается по ожидаемому ключу, нужная учётка имеет выданные права. Только потом освобождай старый сеанс. [Документация sshd](https://man.openbsd.org/sshd)

## 3. Контейнер не держится

**Первые три проверки**

1. **На vulnbox:** посмотри все контейнеры, включая остановленные. Если есть Compose, проверь, что используешь правильный проект из нужного каталога.
2. **На vulnbox:** для проблемного контейнера сравни фазу, код выхода, отметку OOM и число перезапусков. OOM — ситуация нехватки памяти.
3. **На vulnbox:** посмотри первые ошибки около запуска и состояние зависимостей. Сверь изменения образа, конфига и подключённых файлов.

```bash
sudo docker ps -a
sudo docker inspect --format 'status={{.State.Status}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}} restarts={{.RestartCount}}' notes-web
sudo docker logs --timestamps --since 5m --tail 60 notes-web
```

`restarting` или растущее число перезапусков — повод выяснить, почему процесс завершается. `OOMKilled=true` указывает на завершение из-за нехватки памяти. Код `137` сам по себе не доказывает OOM. Если первым сообщением идёт «не найден файл конфигурации», полезнее проверить путь и крепление файла, чем снова перезапустить контейнер.

**Откат.** Если известна последняя правка, верни конкретный параметр запуска, конфиг или образ по порядку проекта. Перед пересозданием проверь постоянные тома и способ запуска. Удаление общего проекта или тома может затронуть данные и другие сервисы. [Откат приложения](./12-patch-and-verify.md)

**Критерий восстановления.** Контейнер остаётся запущенным на интервале наблюдения, штатный сценарий с ПК проходит, старая запись читается. [Список контейнеров](https://docs.docker.com/reference/cli/docker/container/ls/) · [Логи Docker](https://docs.docker.com/reference/cli/docker/container/logs/)

## 4. Сервис отвечает только локально

**Первые три проверки**

1. **С рабочего ПК:** проверь правильный внешний адрес, протокол, порт и штатный путь. Для HTTP в примере можно отправить прямой запрос без прокси.
2. **На vulnbox:** проверь адрес прослушивания. `127.0.0.1` локален. Внешний доступ может идти через обратный прокси или опубликованный порт Docker.
3. **Сверь схему:** сопоставь внешний порт, прокси и порт приложения. Если внешний порт совпадает с заданием, проверь выбор маршрута с ПК и последнее изменение сетевой политики.

```bash
# ПК, для обычного учебного HTTP-маршрута
curl --noproxy '*' -sS -i --connect-timeout 4 --max-time 8 http://10.2.17.2:8080/health

# Vulnbox: слушающие TCP-сокеты
sudo ss -lntp

# Vulnbox: только если этот сервис в Docker
sudo docker port notes-web
```

Если маршрутизация привязана к имени хоста, в проверке пользуйся выданным URL. Подстановка IP вместо имени может привести на соседний виртуальный хост или вызвать штатную ошибку TLS. `/health` — учебный путь. Он подходит, только если такой маршрут есть у вашего приложения.

**Откат.** Верни последнюю сетевую настройку, правило или публикацию порта по её сохранённому значению. Сначала согласуй с ответственным за общую сеть. Широкое ограничение шлюза может сломать штатный доступ.

**Критерий восстановления.** С ПК открывается правильный сервис по выданному адресу, а его обычное действие проходит. [Диагностика сети](./05-network-and-proxy.md)

## 5. HTTP отвечает, Jury красный

**Первые три проверки**

1. Запиши **точный код Jury, тик и время**. Сравни со временем своего запроса. При скрытом или старом табло зафиксируй это.
2. С ПК выполни обычный сценарий целиком. Для «Заметок»: вход → чтение старой учебной записи → создание → чтение новой.
3. В логах своего приложения и прокси найди это действие. Если есть ID запроса, сопоставь его. Проверь последнюю правку и состояние БД.

| Код | Куда сужать поиск |
|---|---|
| `DOWN` | Слой подключения, нужный порт, доступность из нужной сети |
| `MUMBLE` | Первый шаг сценария, на котором получаешь неправильный результат |
| `CORRUPT` | Чтение ранее сохранённых объектов, идентификатор хранилища и доступ к нему |
| `CHECKER_ERROR` | Детали Jury и локальный тест. При неясной причине передай факты организаторам |

`200` на главной может прийти от прокси, кэша или другого маршрута. Даже правильный ответ `/health` подтверждает только предусмотренное в нём поведение. [Коды ForcAD](https://github.com/pomo-mondreganto/ForcAD/wiki/Writing-a-checker)

**Откат.** Если ранее повторяемое действие сломалось сразу после известной правки, верни её по инструкции. Если собственные проверки проходят, а объяснения судьи недостаточно, зафиксируй выводы и передай вопрос организаторам.

**Критерий восстановления.** Свежий пользовательский тест проходит. Следующий статус Jury отмечается отдельно, если табло доступно.

## 6. Пропали старые данные

**Первые три проверки**

1. Убедись, что тестируешь **ту же учётку, запись и инстанс**, что и раньше. Выпиши ID своей учебной заметки и время её создания.
2. Сверь **фактический** конфиг подключения, каталог данных или Docker-том с карточкой до правки.
3. Посмотри, существует ли прежнее хранилище и доступно ли оно вашему процессу. Проверь ошибки доступа, смену роли, миграцию и доступное место. Избегай записи в старую копию во время диагностики.

Для контейнера пригодится выборочный вывод точек монтирования:

```bash
sudo docker inspect --format '{{range .Mounts}}{{println .Type .Name .Source .Destination}}{{end}}' notes-web
```

Если БД в отдельном контейнере, посмотри точки монтирования именно контейнера БД. Если приложение читает из внешней БД, сверяй её экземпляр и имя. Появление новых записей в пустой базе совместимо с тем, что прежняя база всё ещё цела.

**Откат.** Если просто сменился путь, восстанови прежнее подключение. Если хранилище действительно повреждено, сначала сохрани текущее состояние отдельно, проверь копию восстановлением в изолированное место и согласуй переключение. Старый дамп может не содержать новые данные. [Бэкапы и восстановление](./08-backup-and-restore.md)

**Критерий восстановления.** Читается ожидаемая старая учебная запись из постоянного хранилища, создаётся и читается новая. Если в игре уже лежат другие записи и данных не хватает, сообщи команде и владельцу сервиса.

## 7. Закончилось место

**Первые три проверки**

1. По сообщению ошибки определи **путь**, куда приложение хотело писать. Отдельно проверь разделы данных, логов и бэкапов, если они разные.
2. Посмотри свободные блоки через `df -h` и число свободных inode через `df -i`. Inode — структура учёта файловой системы. У файловой системы может закончиться возможность создавать новые объекты, даже если свободные байты ещё есть.
3. Проверь, что занимает место, в конкретном каталоге. Учитывай только вывод своего хоста и конкретную проблемную файловую систему.

```bash
# Vulnbox. Замени /srv/notes/data существующим каталогом данных своего сервиса.
df -h -- /srv/notes/data
df -i -- /srv/notes/data
du -x -h --max-depth=1 -- /srv/notes/data
```

`du -x` ограничивает обход текущей файловой системой, `--max-depth=1` выводит суммы по первому уровню. Команда всё равно читает дерево ниже и может занять время. Если `df` показывает свободное место и inode, проверь квоту, куда реально смонтирован путь, и ограничения контейнера. Если `df` и `du` заметно расходятся, один из вариантов — приложение держит уже удалённый файл открытым. Сначала уточни у владельца процесса и проверь состояние перед решением о перезапуске.

**Восстановление.** Согласуйте перенос или чистку известных временных файлов, которые можно восстановить. Для логов действуйте через штатную ротацию. Сохрани относящийся к инциденту фрагмент. Живую базу, WAL и тома Docker не освобождают ручным удалением.

**Критерий восстановления.** На нужном разделе достаточно места и inode. Штатная операция записи действительно проходит, запись читается, а ошибка не повторяется в свежих логах. [Документация df](https://man7.org/linux/man-pages/man1/df.1.html)

## 8. Когда передать вопрос жюри

Напиши через официальный канал, когда потерян и SSH, и резервный доступ, неизвестен допустимый способ восстановления или локальный тест стабильно проходит при непонятном статусе Jury. Передай номер команды, точный сервис, тик, время с часовым поясом, проверенное действие и краткую ошибку. Пароли, ключи, cookie, токены и флаги не прикладывай.

> Команда 17, «Заметки», тик 8, 11:10:15 по времени площадки. Jury показывает MUMBLE. С игрового ПК вход, чтение старой записи и запись новой прошли в 11:10:23. Последняя правка в 11:08, откат проверен. Можете подсказать, на каком штатном шаге остановилась проверка?

Принцип закрытия инцидента: запиши **что перестало работать, что вернули и чем подтвердили**, включая время. Если результат Jury ещё неизвестен, укажи это как отдельное состояние.
