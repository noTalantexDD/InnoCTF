# InnoCTF Junior · шпаргалка до 10:40

Подготовка рабочего ПК и своего vulnbox по слайдам заключительного этапа. Время — по расписанию площадки. Команды для сервера рассчитаны на Linux, OpenSSH и, где указано, systemd или Docker. Логин, порт SSH, сетевые настройки и перечень сервисов берите из выдачи организаторов.

## Если осталось пять минут

- [ ] Открой новый SSH-сеанс по своему ключу. Проверь `sudo -v`, если выдана учётка с sudo. Держи старый сеанс или консоль открытыми.
- [ ] С рабочего ПК проверь, что каждый игровой сервис отвечает на **штатный** запрос. Сверь порты и список из задания.
- [ ] Проверь, какие приложения уже скопированы с vulnbox и где лежат их данные. Если время поджимает, начни с конфигов, которые собираешься менять.
- [ ] Открой Jury, если он уже доступен. В 10:40 смотри первые результаты чекера и сопоставляй их со своими проверками.
- [ ] Если после последней правки что-то перестало работать, откати именно эту правку и проверь сервис снова.

## 1. Расписание и карта сети

| Время | Что делать |
|---|---|
| 09:00–10:00 | Настроить рабочие ПК, подготовить ключи, инструменты и командную заметку |
| 10:00–10:12 | Получить vulnbox, сменить пароль, добавить и проверить ключи, настроить SSH |
| 10:12–10:25 | Записать сервисы, порты и исходные результаты штатных проверок |
| 10:25–10:35 | Сохранить код, конфиги и данные, проверить локальные копии |
| 10:35–10:40 | Повторить проверки, закончить правки, открыть Jury |

По слайдам vulnbox выдают в 10:00, межкомандную сеть открывают в 10:40. В таблице внутренние сроки предложены для работы команды.

| Что | Адрес из презентации |
|---|---|
| Командная сеть | `10.2.X.0/24` |
| Свой vulnbox | `10.2.X.2` |
| Командный шлюз | `10.2.X.1` |
| Jury / ForcAD | `http://10.10.10.10/` |
| HTTP-прокси площадки | `http://10.10.10.10:8080` |
| Сертификат прокси | `http://10.10.10.10:8080/cert` |

`X` — значение из выдачи организаторов. `LOGIN`, `PORT`, `UNIT`, `CONTAINER` и прочие заглавные обозначения в примерах замени реальными значениями. `22` в командах — стандартный порт SSH, при необходимости замени его.

С раундом в 2 минуты и `flag lifetime: 5` флаг действует пять раундов, около десяти минут игрового времени. Чекер проверяет доступность и работу игровых сервисов. Открытая главная страница — только первое измерение. Сервис также должен выполнять штатные операции. Точную трактовку статусов смотри в интерфейсе Jury и правилах площадки.

## 2. 09:00–10:00. Рабочее место

1. Подключись к сети площадки выданным способом. Уточни, как получить консоль vulnbox, если SSH перестанет отвечать.
2. Если на рабочем ПК выдали сменяемый пароль Linux-учётки, выполни `passwd`. У каждого участника свой ключ, у команды один ответственный за изменение настроек SSH и сети.
3. Открой редактор, терминал и браузер. Проверь `ssh -V` и `curl --version`. Подготовь `scp`, `tar` и `sha256sum` или их аналоги. `tmux`, `git` и `rg` пригодятся, если доступны.
4. Jury и свой vulnbox открывай напрямую из игровой сети. Если нужен доступ к разрешённым внешним сайтам, используй прокси площадки. Он пропускает только разрешённый список сайтов и GET по условиям слайда. На своём ПК удобнее отдельный профиль браузера с настройками прокси. Сертификат подключай по инструкции организаторов и только для нужного профиля или инструмента.
5. Сохрани шпаргалку локально. Заведи командную заметку с инвентарём сервисов и временем правок. Пароли, приватные ключи, токены, конфиги с секретами и дампы держите в защищённом месте команды.

### SSH-ключ участника

На рабочем ПК, в Linux или WSL:

```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh
ssh-keygen -t ed25519 -f ~/.ssh/innoctf_ed25519 -C "participant-innoctf"
```

Если это имя уже занято, выбери другое. Файл `innoctf_ed25519.pub` можно передать ответственному за SSH. Второй файл — приватный ключ. В Windows с OpenSSH аналогичный путь можно построить от `$env:USERPROFILE` в PowerShell.

### Распределение работы

| Кто | Задача после выдачи |
|---|---|
| Ответственный за доступ | SSH, ключи, первый сеанс для отката, связь с организаторами |
| Ответственные за сервисы | Инвентарь, штатные проверки, бэкапы и точечные правки |
| Кто следит за Jury | Статусы, время изменений, сообщение команде о первом сбое |

Если вас двое, один ведёт доступ, второй начинает инвентарь сразу после получения ключа. До подтверждения первого входа задачи сервера можно распределять по списку организаторов.

## 3. 10:00–10:12. SSH без потери доступа

### 3.1 Сначала сохрани рабочий сеанс

С рабочего ПК зайди по выданному логину. Если сервер новый, при возможности сверь его отпечаток с данными площадки. Если известный отпечаток вдруг изменился, сверь его через консоль или у организаторов до продолжения.

```bash
ssh -p 22 LOGIN@10.2.X.2
```

Уже на vulnbox:

```bash
whoami
hostname
id
passwd
sudo -v
```

Под `root` административные команды выполняются без `sudo`. Для `passwd` меняй выданную тебе учётку. **Оставь этот сеанс открытым** и подготовь отдельный терминал для проверок.

### 3.2 Добавь ключи, проверь каждый, потом убери лишние

На рабочем ПК:

```bash
ssh-copy-id -i ~/.ssh/innoctf_ed25519.pub -p 22 LOGIN@10.2.X.2
ssh -p 22 -i ~/.ssh/innoctf_ed25519   -o IdentitiesOnly=yes -o PreferredAuthentications=publickey   -o ControlPath=none LOGIN@10.2.X.2
```

Если `ssh-copy-id` отсутствует, добавь строку из `.pub` в файл авторизованных ключей целевого пользователя. Для стандартного пути на vulnbox сделай `mkdir -p ~/.ssh`, `chmod 700 ~/.ssh`, открой `~/.ssh/authorized_keys` в редакторе и добавь ключ с новой строки. После сохранения выполни `chmod 600 ~/.ssh/authorized_keys`. Владельцем файлов должен быть нужный пользователь. Точный путь зависит от `AuthorizedKeysFile`.

В новом сеансе проверь `id` и `sudo -v`. Пусть каждый участник подтвердит свой вход. Сверь отпечатки через `ssh-keygen -lf ~/.ssh/innoctf_ed25519.pub` на рабочем ПК и `ssh-keygen -lf ~/.ssh/authorized_keys` на сервере, если используется стандартный путь. Перед удалением лишних строк сделай копию файла. Ключи, которые организаторы обозначили как служебные, сохрани. После правки снова проверь новый вход.

### 3.3 Отключи парольный SSH

Найди действующие настройки (на vulnbox):

```bash
sudo sshd -T | awk '/^(pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication|authorizedkeysfile|authenticationmethods) /'
sudo rg -ni '^[[:space:]]*(include|match|pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication|authenticationmethods)\b'   /etc/ssh/sshd_config /etc/ssh/sshd_config.d
```

Если каталога `sshd_config.d` или `rg` нет, проверь основной файл и пути из его `Include` в редакторе. Перед изменением сохрани копию **каждого** редактируемого файла. Для основного конфига пример такой:

```bash
sudo cp -a /etc/ssh/sshd_config /etc/ssh/sshd_config.innoctf-before
sudoedit /etc/ssh/sshd_config
```

Итоговые значения для командного доступа:

```text
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
```

В OpenSSH порядок важен. Проверь `Include`, существующие значения и условные блоки `Match`. Если такие блоки есть, дополнительно проверь итог для своей учётки и IP рабочего ПК:

```bash
sudo sshd -T -C user=LOGIN,addr=CLIENT_IP,laddr=10.2.X.2,lport=22   | awk '/^(pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication|authenticationmethods) /'
```

Проверь синтаксис с `sudo sshd -t`. Если команда вернула ошибку, сначала исправь её. Если проверка прошла, используй `sudo systemctl reload ssh` или `sudo systemctl reload sshd` в зависимости от названия юнита. Для системы без systemd уточни штатную команду на площадке.

С рабочего ПК снова открой **новый** сеанс командой с ключом. Затем отдельно убедись, что сервер не предлагает пароль:

```bash
ssh -p 22 -o PubkeyAuthentication=no   -o PreferredAuthentications=password,keyboard-interactive   -o ControlPath=none LOGIN@10.2.X.2
```

Ожидается отказ в аутентификации без запроса пароля пользователя. Запрос парольной фразы ключа при **положительном** тесте — локальная разблокировка ключа. Запрос пароля через `sudo` после входа тоже нормален.

**Если новый SSH-сеанс сломался:** из старого сеанса восстанови изменённый файл из своей копии, проверь `sudo sshd -t`, перезагрузи конфигурацию тем же `reload` и повтори новый вход. Если менялся основной конфиг, команда восстановления — `sudo cp -a /etc/ssh/sshd_config.innoctf-before /etc/ssh/sshd_config`. При правке включаемого файла верни именно его. Если старый сеанс потерян, используй консоль площадки.

## 4. 10:12–10:25. Инвентарь и проверка сервисов

Начни с официального списка сервисов, затем сопоставь с тем, что реально запущено. Команды выполняй на своём vulnbox.

```bash
ip -br address
ip route
sudo ss -lntup
systemctl --type=service --state=running --no-pager
df -h
```

Если есть Docker:

```bash
sudo docker ps -a
sudo docker compose ls
sudo docker inspect --format '{{json .Mounts}}' CONTAINER
```

Если сервис под systemd:

```bash
systemctl status UNIT --no-pager
systemctl show UNIT -p FragmentPath -p WorkingDirectory
sudo journalctl -u UNIT --since "10 minutes ago" --no-pager
```

Если сервис в контейнере:

```bash
sudo docker logs --since 10m --tail 100 CONTAINER
# Из каталога соответствующего compose.yaml
sudo docker compose ps --all
```

| Сервис | Порт с ПК | Юнит / контейнер | Код и конфиги | Данные | Штатная проверка | Кто отвечает |
|---|---|---|---|---|---|---|
| Заполнить | | | | | | |

В `ss` адрес `127.0.0.1` означает локальное прослушивание. `0.0.0.0` означает все IPv4-интерфейсы, а `[::]` — все IPv6-интерфейсы. Для Docker отдельно проверь публикацию порта. Например, `0.0.0.0:8080->80/tcp` означает, что с рабочего ПК нужно обращаться к порту `8080` хоста.

Для известного HTTP-маршрута, с рабочего ПК:

```bash
curl --noproxy '*' -sS -i --max-time 5 "http://10.2.X.2:PORT/KNOWN_PATH"
```

Для HTTPS или другого протокола используй его штатный клиент. Запиши, какой ответ и поведение были **до** изменений. Если доступно только локально, а на ПК таймаут, проверь адрес прослушивания, опубликованный порт, маршрут и правила фильтрации. Если вернулся `404`, сверь маршрут. Если `500`, смотри логи приложения и состояние его зависимостей.

По слайду межкомандные запросы приходят со шлюза `10.2.X.1`. Блокировка шлюза целиком лишит сервисы части игрового трафика. Для лишнего порта сначала установи процесс, назначение порта и зависимости. Меняй только конкретный порт с понятным планом отката, затем проверь SSH и игровой сервис с рабочего ПК.

## 5. 10:25–10:35. Бэкапы и точечные правки

Сохрани для каждого сервиса:

- Код и конфиги приложения, файлы Compose или юнит systemd с относящимися к нему настройками запуска.
- Данные из отдельных каталогов, bind mounts и именованных томов. Для живой БД используй её штатный механизм экспорта.
- Исходные пути, владельца файлов и способ перезапуска. Это нужно для отката. Для изменения одного конфига обычно достаточно восстановить прежний конфиг и перечитать настройки сервиса.

### Архив кода и конфигов

Допустим, каталог сервиса — `/opt/myservice`. Выбери уникальное имя для каждой попытки бэкапа и подставь реальный каталог.

```bash
# Свой vulnbox, под учёткой, которой будешь скачивать
umask 077
mkdir -p "$HOME/ad-backup"
df -h "$HOME" /opt
archive="$HOME/ad-backup/myservice-before.tar.gz"
sudo tar -C /opt -czf - myservice > "$archive" &&
  tar -tzf "$archive" > /dev/null &&
  sha256sum "$archive"
```

Если любая команда завершилась с ошибкой, исправь причину и создай копию заново под новым именем. Затем скачай:

```bash
# Рабочий ПК, Linux / WSL
mkdir -p -m 700 ad-backup
scp -P 22 -i ~/.ssh/innoctf_ed25519   LOGIN@10.2.X.2:ad-backup/myservice-before.tar.gz ./ad-backup/
sha256sum ./ad-backup/myservice-before.tar.gz
```

В PowerShell хеш файла покажет `Get-FileHash .\ad-backup\myservice-before.tar.gz -Algorithm SHA256`. Сравни оба хеша. Архив можно сначала распаковать в отдельный временный каталог и проверить состав. Данные живого приложения восстанавливай только тогда, когда это действительно нужно. Возврат старого дампа может стереть более новые записи.

### Контейнеры и базы данных

| Где данные | Что сохранить |
|---|---|
| Bind mount | Каталог хоста из `docker inspect` и привязку к пути в контейнере |
| Именованный Docker-том | Копию тома через штатный способ резервного копирования. Для живой БД сначала сделай логический дамп |
| PostgreSQL | Дамп своей БД с разрешённой учёткой. Для архива `pg_dump -Fc -d DBNAME > backup.dump` проверь, что `pg_restore -l backup.dump` читает оглавление |
| SQLite | Резервную копию через `sqlite3 /path/to/app.db ".backup '/path/to/backup.db'"`, если есть клиент и права. Оригинал может иметь WAL |
| Данные внутри слоя контейнера | Уточни расположение и скопируй нужные файлы. Одна копия `compose.yaml` их не содержит |

В примерах используются локальная конфигурация клиента и выданные права. Сохраняй дампы в закрытом каталоге. Отдельно проверь, что у тебя есть локальная копия, открываемая без доступа к vulnbox.

### Порядок изменений

1. Возьми один сервис и запиши исходный статус.
2. Сохрани изменяемый файл и его точный путь.
3. Сделай одну небольшую правку. Если есть штатная проверка конфига, запусти её.
4. Примени изменение штатным для этого сервиса способом. Повтори проверку с рабочего ПК и посмотри свежие логи.
5. При сбое верни предыдущую версию файла, перечитай конфиг и снова проверь. Передай команде статус и время.

Устанавливай на сервер только то, что нужно прямо сейчас. При коротком окне приоритет у доступа, бэкапов и проверки штатных сценариев. Массовое обновление пакетов или пересоздание всех контейнеров займёт время и усложнит поиск причины сбоя.

## 6. 10:35–10:40. Финальный прогон и быстрые развилки

- [ ] Вход по ключу проверен в новом SSH-сеансе. Известен доступ к консоли.
- [ ] Парольная аутентификация выключена и проверена отдельно.
- [ ] Обязательные порты, штатные действия и состояние контейнеров или юнитов проверены с нужной стороны сети.
- [ ] Архивы проверены, скачаны и подписаны по именам сервисов.
- [ ] Есть ответственный за первый результат Jury и известно, кто откатывает каждую последнюю правку.

| Симптом | Что проверить первым |
|---|---|
| SSH таймаутит | IP и порт из выдачи, подключение к сети площадки, затем слушающий порт через консоль |
| SSH выдаёт `Permission denied (publickey)` | Логин, выбранный приватный ключ, владельца и права на сервере, `AuthorizedKeysFile` и `Match` |
| `sshd -t` прошёл, а вход после reload пропал | Старый сеанс или консоль, вернуть изменённые конфиги, проверить действующую политику и повторить reload |
| Локально HTTP работает, с ПК — нет | Адрес прослушивания, проброс порта Docker, настройки сети и прокси |
| HTTP открывается, а сервис у Jury красный | Проверить полный штатный сценарий и логи за время проверки. Сверить время последней правки. При явной связи откатить её |
| Бэкап есть только на сервере | Скачать `scp`, сверить хеш и записать локальный путь |
| Jury недоступен до старта | Уточнить доступность у площадки и продолжить локальные проверки. Повторить попытку после открытия сети |
