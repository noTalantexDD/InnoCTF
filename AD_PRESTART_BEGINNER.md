# InnoCTF A/D с нуля — пошаговый гайд до 10:40

Это подробная версия [AD_PRESTART.md](./AD_PRESTART.md) для участника, который впервые видит Attack/Defense. Можно идти по порядку и отмечать выполненное. Если команда уже сделала шаг, попроси показать результат проверки.

## 0. Что происходит на A/D

Представь, что вам выдали сервер с сайтом заметок. Этот сервер называется **vulnbox**. Судейская программа, **чекер**, пользуется сайтом как обычный клиент: например, создаёт заметку с секретной строкой (**флагом**) и позже читает её. Если сайт открывается, но после вашей правки старые заметки пропали, чекер всё равно может поставить ошибку. На табло это влияет на оценку работы сервиса и очки.

A/D — Attack/Defense. Команды защищают свои сервисы, а игровая система начисляет очки за игровые флаги и учитывает работу сервисов. Твоя задача в этом гайде — сохранить доступ к своему серверу, понять, что на нём запущено, и подготовить рабочий откат.

| Время площадки | Что происходит | Что должно быть у тебя |
|---|---|---|
| 09:00–10:00 | Подготовка рабочих ПК | Терминал, SSH-ключ, известные адреса, распределённые роли |
| 10:00–10:12 | Начало закрытого окна после выдачи | Открытый запасной сеанс, вход по проверенному ключу |
| 10:12–10:25 | Инвентаризация | Перечень сервисов и результаты штатных проверок до правок |
| 10:25–10:35 | Бэкапы и точечные исправления | Копии кода, конфигов и данных, понятный способ отката |
| 10:35–10:40 | Финальный прогон | SSH, сервисы и копии проверены, открыт Jury, если доступен |

10:12, 10:25 и 10:35 — ориентиры для работы. Официальное закрытое окно длится **10:00–10:40**. По слайдам сеть открыта с 10:40 до 13:00, с 13:00 до 14:00 закрыта на обед, с 14:00 до 16:30 снова открыта. На 16:30–17:00 указано закрытие скорборда, конец игры в 17:00. Актуальные объявления площадки важнее таблицы.

## 1. Как читать каждую команду

**ПК** — твой компьютер. **VULNBOX** — сервер после входа по SSH. Держи три вкладки терминала и подпиши их:

| Вкладка | Что в ней делать |
|---|---|
| **ПК** | Создать ключ, открывать SSH, проверять веб-сервисы, скачивать копии |
| **VULNBOX A** | Первый работающий SSH-сеанс. Оставить открытым для отката |
| **VULNBOX B** | Новый сеанс для проверки ключей и работы на сервере |

Если сомневаешься, где находишься, выполни `hostname`. `whoami` показывает, под каким пользователем ты вошёл. `pwd` показывает текущий каталог. `exit` завершает текущий SSH-сеанс, так что запасную вкладку A не закрывай, пока она нужна.

Строки после `#` — поясняющие комментарии. Примеры ниже рассчитаны на Bash. `~` и `$HOME` означают домашнюю папку текущей учётки. На ПК и сервере это две разные папки. Пароль при вводе в Linux обычно вообще не отображается, даже звёздочками. Вводишь и нажимаешь Enter. `Ctrl+C` может прервать выполняющуюся команду. Вывод в терминале сам по себе ещё не означает успех: сверяйся с ожидаемым результатом шага.

В сетевых примерах ниже **условная команда №17**, пользователь `player`, SSH-порт `22`. Перед копированием подставь свои значения. `UNIT`, `CONTAINER` и `DBNAME` тоже заменяются реальными именами. Угловые скобки вида `<порт>` из короткой шпаргалки в Bash означают перенаправление, поэтому их не вставляют в команду буквально.

| Что выдали | В примере | Где взять своё |
|---|---|---|
| Номер команды / значение `X` | `17` | Из выдачи организаторов |
| Свой vulnbox | `10.2.17.2` | Из выдачи, на слайде схема `10.2.X.2` |
| Подсеть и шлюз | `10.2.17.0/24` и `10.2.17.1` | Из выдачи. `/24` здесь означает, что первые три части задают сеть |
| SSH-логин и порт | `player` и `22` | Из выдачи. `22` используется, если организаторы не указали другой порт |
| Jury / ForcAD | `http://10.10.10.10/` | Судейское табло. Порт HTTP `80` можно опустить |
| Прокси и его сертификат | `http://10.10.10.10:8080` и `http://10.10.10.10:8080/cert` | Из инструкции площадки |

Прокси обслуживает разрешённые внешние сайты. По слайду там разрешён только HTTP-метод `GET`. Jury и свой vulnbox открывай напрямую через игровую сеть. Со стороны vulnbox межкомандные запросы видны с адреса шлюза `10.2.X.1`. По одному этому адресу нельзя определить исходную команду.

В игре тик длится **2 минуты**. `flag lifetime: 5` — пять раундов, то есть около десяти минут игрового времени. По слайду на уязвимость предусмотрено два флага. `attack_data` — опубликованные платформой игровые данные, которые может возвращать чекер, например имя тестового пользователя. `hardness` и `score` — параметры подсчёта очков.

## 2. До 10:00 — подготовь ПК

### 2.1 Проверь сеть и инструменты

**Где:** на рабочем ПК. Подключись способом, который дал организатор. Уточни, есть ли консоль vulnbox на случай, если SSH станет недоступен. Если Jury уже открыт для участников, проверь его в браузере.

```bash
ip -br address
ip route
ssh -V
curl --version
command -v scp tar sha256sum nano
```

- `ip -br address` кратко показывает интерфейсы и назначенные им адреса.
- `ip route` показывает маршруты. При нескольких сетях можно спросить Linux, куда он отправит пакет, командой `ip route get 10.10.10.10`. Посмотри на `dev` — интерфейс, и `src` — исходный адрес.
- `ssh -V` и `curl --version` показывают версии программ. Вывод версии SSH может появиться в потоке ошибок, это ожидаемо.
- `command -v` печатает пути к найденным программам. Если `nano` отсутствует, используй знакомый редактор. На Windows эти примеры проще запускать в WSL, если он доступен. В PowerShell проверяй доступность SSH командой `Get-Command ssh,scp`.

Если на рабочем Linux-ПК выдали пароль, который разрешили менять, выполни `passwd`. Обычно нужно ввести старый пароль и дважды новый. `systemctl is-active ssh` проверяет **входящий SSH-сервер на текущей машине**. `inactive` на рабочем ПК совместим с тем, что команда `ssh` прекрасно подключается наружу. Если показывает `active`, сначала выясни, нужен ли этот сервер площадке.

### 2.2 Сделай SSH-ключ

**Где:** на ПК. Выполни по строкам:

```bash
mkdir -p "$HOME/.ssh"
chmod 700 "$HOME/.ssh"
ssh-keygen -t ed25519 -f "$HOME/.ssh/ctf_ed25519" -C "$(whoami)-ctf"
ssh-keygen -lf "$HOME/.ssh/ctf_ed25519.pub"
```

1. `mkdir -p` создаёт папку при необходимости. `chmod 700` оставляет доступ к ней владельцу.
2. `-t ed25519` выбирает тип ключа, `-f` — путь для файлов, `-C` добавляет подпись текущего пользователя.
3. Если увидишь вопрос о перезаписи существующего ключа, ответь `n` и выбери другое имя файла. Дальше используй новое имя везде.
4. Когда `ssh-keygen` предложит парольную фразу, она будет защищать приватный ключ на твоём ПК. Вводится дважды.
5. Получишь два файла. `ctf_ed25519.pub` — публичный, его можно отдать ответственному за SSH. `ctf_ed25519` — приватный, он остаётся у тебя.
6. Последняя команда печатает **отпечаток** ключа, обычно начинается с `SHA256:`. Его удобно сверить на сервере.

Если вы собираете `team_keys.pub`, в нём должна быть ровно одна строка на каждый публичный ключ участника. Таблица «имя участника → отпечаток» поможет понять, кому принадлежит каждая строка на сервере.

### 2.3 Прокси и дополнительные программы

Прокси понадобится, только если нужно выйти на разрешённый внешний сайт или скачать пакеты заранее. Адрес самого прокси и адрес для загрузки сертификата — разные вещи. Если организаторы подтверждают адрес и порядок установки, команда для **загрузки файла** выглядит так:

```bash
curl --noproxy '*' -fS --max-time 10   -o proxy-ca.crt http://10.10.10.10:8080/cert
```

`--noproxy '*'` делает этот запрос напрямую, `-f` завершает команду ошибкой при HTTP 4xx/5xx, `-S` показывает ошибки, `-o` сохраняет ответ в указанный файл. Дальше сертификат устанавливай по инструкции площадки. Если площадка дала контрольный отпечаток, сверь его. Для личного ПК предпочтителен игровой профиль браузера или доверие к CA в конкретном инструменте. Установка CA в системное хранилище добавляет доверие для многих программ сразу.

Какие пакеты упомянуты в оригинале: `tmux` держит несколько терминальных сессий, `git` отслеживает изменения кода, `rsync` синхронизирует файлы, `ripgrep` даёт команду `rg` для поиска по тексту. `tcpdump` и `tcpflow` используются для сетевой диагностики. `pip download` заранее скачивает Python-пакеты и зависимости в каталог, но совместимость зависит от Python, архитектуры и ОС. Для новичка первый приоритет — рабочие `ssh`, `scp`, `curl` и редактор.

Роли: один человек ведёт SSH, другой составляет таблицу сервисов, ответственный за Jury отмечает статусы и время изменений. Вдвоём просто совмещайте роли.

## 3. 10:00 — получи доступ к vulnbox

### 3.1 Первый вход и пароль

**Где:** на ПК, отдельная вкладка, которая станет **VULNBOX A**.

```bash
ssh -p 22 player@10.2.17.2
```

`-p 22` задаёт порт. Запись `player@10.2.17.2` читается «пользователь player на сервере с этим IP». При первом входе клиент может показать отпечаток **ключа сервера** и попросить подтвердить его. Сверь с данными организаторов или консоли. Если известный отпечаток внезапно изменился, выясни причину до подключения.

Когда зайдёшь, выполни на **VULNBOX A**:

```bash
hostname
whoami
id
passwd
sudo -v
```

`id` покажет идентификатор и группы текущей учётки. `passwd` меняет пароль текущей учётки. При общей учётке согласуй смену с командой. `sudo -v` проверяет возможность получить предусмотренные для учётки права и может попросить её пароль. Если выдан `root`, команды для администратора обычно выполняются без `sudo`. **Вкладку A держи открытой.**

Если SSH выдаёт `Connection timed out`, проверь адрес, порт и сеть площадки. `Connection refused` означает, что соединение активно отклонено, например на порту никто не слушает. `Permission denied` означает, что до сервера ты дошёл и проблема сейчас на этапе входа.

### 3.2 Добавь ключ и докажи, что он работает

**Где:** на ПК, в другом терминале. Старую сессию A оставь открытой.

```bash
ssh-copy-id -i "$HOME/.ssh/ctf_ed25519.pub" -p 22 player@10.2.17.2

ssh -p 22 -i "$HOME/.ssh/ctf_ed25519"   -o IdentitiesOnly=yes -o PreferredAuthentications=publickey   -o ControlPath=none player@10.2.17.2
```

`ssh-copy-id` добавляет публичный ключ в учётку на сервере. Во второй команде `-i` выбирает приватный ключ на ПК, `IdentitiesOnly=yes` ограничивает предлагаемые ключи выбранными идентификаторами, `PreferredAuthentications=publickey` выбирает вход ключом, `ControlPath=none` позволяет проверить действительно новое соединение. Новый терминал после входа — **VULNBOX B**. Проверь там `whoami` и `sudo -v`. Локальный запрос парольной фразы от ключа ожидаем.

Если `ssh-copy-id` отсутствует, на сервере под **целевой учёткой** выполни:

```bash
mkdir -p "$HOME/.ssh"
chmod 700 "$HOME/.ssh"
touch "$HOME/.ssh/authorized_keys"
chmod 600 "$HOME/.ssh/authorized_keys"
nano "$HOME/.ssh/authorized_keys"
```

Вставь публичный ключ отдельной строкой, сохрани в Nano через `Ctrl+O` → Enter → `Ctrl+X`. `touch` сохраняет имеющееся содержимое. `600` оставляет владельцу чтение и запись. Если у сервера нестандартный `AuthorizedKeysFile`, путь уточняет ответственный за SSH через `sshd -T`. После добавления каждого ключа участник проверяет **новый вход**.

### 3.3 Убери только подтверждённо лишние ключи

Отпечаток каждого участника есть на его ПК. На **VULNBOX A**, под целевой учёткой и при стандартном пути:

```bash
cp -a "$HOME/.ssh/authorized_keys" "$HOME/.ssh/authorized_keys.before"
ssh-keygen -lf "$HOME/.ssh/authorized_keys"
ls -ld "$HOME/.ssh" "$HOME/.ssh/authorized_keys"
```

`cp -a` сохраняет копию с атрибутами. `ssh-keygen -lf` позволяет сверить отпечатки, `ls -ld` — владельца и права. Сравни со списком команды. Если назначение ключа неизвестно, уточни у организаторов, прежде чем удалить. Затем проверь новый вход всеми нужными ключами. Если после правки ключ перестал работать, в сеансе A верни копию через `cp -a "$HOME/.ssh/authorized_keys.before" "$HOME/.ssh/authorized_keys"`. Для этой правки SSH перезагружать не нужно.

## 4. Отключи вход по паролю и сохрани путь назад

**Причина:** команда переходит на вход по ключу после того, как ключ и административные права работают. `PasswordAuthentication` и `KbdInteractiveAuthentication` — два вида аутентификации, которые могут показывать запрос пароля.

### 4.1 Посмотри, что действует сейчас

На **VULNBOX A**:

```bash
sudo sshd -T | grep -Ei '^(pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication|permitrootlogin|authorizedkeysfile|authenticationmethods) '
sudo grep -nEi '^[[:space:]]*(include|match|passwordauthentication|kbdinteractiveauthentication|pubkeyauthentication|authenticationmethods)([[:space:]]|$)' /etc/ssh/sshd_config
systemctl status ssh --no-pager
```

`sshd -T` выводит действующие настройки, `grep` оставляет нужные строки. `Include` подключает другие конфиги, `Match` задаёт условные правила, например для отдельного логина. Посмотри включённые файлы тоже. Если `ssh.service` отсутствует, проверь `systemctl status sshd --no-pager`. На системе без systemd команда применения настроек может отличаться.

Если найден `Match`, проверь конкретное подключение. В примере `10.2.17.23` — условный IP рабочего ПК:

```bash
sudo sshd -T -C user=player,addr=10.2.17.23,laddr=10.2.17.2,lport=22   | grep -Ei '^(pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication|authenticationmethods) '
```

`user` — SSH-логин, `addr` — адрес клиента, `laddr` и `lport` — адрес и порт сервера. Фактические адреса стороны текущего сеанса видны в `printf '%s\n' "$SSH_CONNECTION"`. При условии `Match Host` включи фактическое имя клиента через `host=...`.

### 4.2 Измени один конфиг и проверь до применения

Сохрани отдельную копию **каждого изменяемого файла**. Для основного конфига последовательность такая:

```bash
sudo cp -a /etc/ssh/sshd_config /etc/ssh/sshd_config.before-ad
sudoedit /etc/ssh/sshd_config
```

Отредактируй действующие глобальные значения или соответствующие настройки в подключённом файле. Учитывай порядок и условия `Match`. Если используешь новый файл, как в оригинале, сначала проверь, что `Include` реально читает этот каталог и нужный файл применяется. Запиши точный путь нового файла как часть плана отката.

```text
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
```

В оригинале также есть `PermitRootLogin no`. Это отключает удалённый вход под root. Применяй эту настройку только после того, как проверил другой предусмотренный организаторами административный логин. Если вам выдали только root-доступ, не отрезай свою единственную учётку. При явном `AuthenticationMethods` проверь, что политика не требует выключенный только что метод.

```bash
sudo sshd -t
sudo sshd -T | grep -Ei '^(pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication) '
```

Первая команда проверяет синтаксис. Если она ничего не печатает и возвращает успех, это нормально. Вторая должна показать `pubkeyauthentication yes`, `passwordauthentication no` и `kbdinteractiveauthentication no`. Если есть `Match`, повтори и контекстную проверку из предыдущего шага. Если результат совпал с планом, примени настройки:

```bash
sudo sshd -t && sudo systemctl reload ssh
```

`&&` запускает следующую команду только при успехе предыдущей. `reload` перечитывает настройки. Если юнит называется `sshd`, подставь его.

### 4.3 Две проверки и откат

1. С ПК снова выполни команду из `3.2` с ключом. Открытие нового сеанса подтверждает именно новый вход.
2. С ПК отдельно проверь парольные методы:

```bash
ssh -p 22 -o PubkeyAuthentication=no   -o PreferredAuthentications=password,keyboard-interactive   -o ControlPath=none player@10.2.17.2
```

Ожидается отказ **без запроса пароля учётки**. Таймаут сам по себе этот результат не подтверждает. Если ключ перестал пускать, верни на вкладке A файлы, которые менял. Для основного файла:

```bash
sudo cp -a /etc/ssh/sshd_config.before-ad /etc/ssh/sshd_config
sudo sshd -t && sudo systemctl reload ssh
```

Если добавлял **новый** `/etc/ssh/sshd_config.d/00-hardening.conf`, сначала перемести именно созданный тобой файл за пределы подключаемого каталога, затем повтори `sshd -t` и `reload`. Восстановление только основного файла может оставить новый drop-in действующим. Если редактировал существующий drop-in, верни его копию. После отката проверь новое подключение. Если вкладка A уже потеряна, переходи в консоль площадки.

## 5. Быстро проверь, кто и что уже запущено

Проверки из оригинала относятся к **своей машине**. Их вывод — инвентарь, а не готовое доказательство взлома. Если время заканчивается, сначала доступ и игровые сервисы.

```bash
last -n 20
w
sudo ls -ld /etc/cron* /var/spool/cron/crontabs
systemctl list-timers --all
```

`last` показывает недавние записи входа, `w` — текущие сеансы. `cron` и таймеры systemd запускают задачи по расписанию. `ls -ld` здесь показывает существование каталогов и права. Отсутствие конкретного пути может быть нормальным для этой ОС. Подозрительное имя сначала сверяй с выдачей и конфигурацией.

В коротком файле также есть `sudo find / -perm -4000 -type f 2>/dev/null`. Это поиск обычных файлов с битом SUID, который позволяет программе запускаться с правами её владельца. `2>/dev/null` скрывает сообщения об ошибках поиска. На живом соревновании полное сканирование дисков может быть лишним: сначала уточни исходное состояние у организаторов, а если действительно нужно искать, начни с системных каталогов. Наличие SUID само по себе нормально для части системных утилит. Права незнакомым файлам вслепую не меняй.

## 6. 10:12–10:25 — составь карту сервисов

На **vulnbox**:

```bash
sudo ss -lntup
systemctl --type=service --state=running --no-pager
sudo docker ps -a
sudo docker compose ls
```

- `ss` показывает сокеты. `-l` — слушающие, `-n` — числовые адреса и порты, `-t` — TCP, `-u` — UDP, `-p` — связанный процесс. Найди столбец с локальным адресом и портом.
- `systemctl` перечисляет запущенные системные службы. Служба systemd обозначается юнитом, например `notes.service`.
- `docker ps -a` показывает и работающие, и остановленные контейнеры. `docker compose ls` показывает проекты Compose. Если Docker отсутствует, продолжай с `ss` и systemd.
- `127.0.0.1:8080` доступен локально на этой машине. `0.0.0.0:8080` слушает на всех IPv4-интерфейсах. `[::]:8080` — на всех IPv6-интерфейсах, а поведение для IPv4 зависит от настроек.
- `0.0.0.0:8080->80/tcp` у Docker означает, что рабочий ПК идёт на порт **8080 хоста**, а внутри контейнера приложение принимает на **80**.

Пример для systemd. Замени `notes.service` на настоящее имя:

```bash
systemctl status notes.service --no-pager
systemctl show notes.service -p FragmentPath -p WorkingDirectory
sudo journalctl -u notes.service --since "10 minutes ago" --no-pager
```

`status` показывает состояние, `FragmentPath` — путь к файлу юнита, `WorkingDirectory` — рабочую папку, если она явно указана. `journalctl -u` показывает журнал конкретного юнита. Смотри время и ошибки после своего запроса.

Пример для контейнера. Замени `notes-web` на настоящее имя:

```bash
sudo docker inspect --format '{{json .Mounts}}' notes-web
sudo docker logs --since 10m --tail 100 notes-web
```

`.Mounts` покажет каталог или том с данными. Смотри `Source`, `Destination` и `Type`. `docker logs` выводит записи контейнера максимум за последние десять минут и ограничивает количество строк. Из каталога с нужным `compose.yaml` можно выполнить `sudo docker compose ps --all`, чтобы увидеть контейнеры проекта и порты.

| Сервис | Порт с ПК | Юнит / контейнер | Где код и конфиг | Где данные | Штатное действие | Бэкап / ответственный |
|---|---|---|---|---|---|---|
| Пример: заметки | `8080/tcp` | `notes-web` | `/opt/notes` | том приложения или отдельная БД | Открыть приложение и прочитать тестовую заметку | Заполнить по выдаче |
| Ваш сервис | | | | | | |

### 6.1 Зафиксируй нормальный ответ до правок

**Где:** на ПК. `/health` здесь пример, его надо заменить известным маршрутом приложения:

```bash
curl --noproxy '*' -sS -i --max-time 5 "http://10.2.17.2:8080/health"
```

`-sS` убирает индикатор загрузки, сохраняя вывод ошибок. `-i` включает заголовки HTTP. `--max-time 5` ограничивает время пятью секундами. `--noproxy '*'` отправляет запрос напрямую.

| Что увидел | Как читать |
|---|---|
| `200` и ожидаемое содержимое | Этот запрос проходит |
| `301` или `302` | Сервер перенаправляет. Проверь заголовок `Location` |
| `401` или `403` | Сервер ответил. Маршрут может требовать вход или права |
| `404` | Сервер ответил, но этот путь не найден |
| `500` | Сервер дошёл до обработки и вернул внутреннюю ошибку. Смотри логи |
| `Connection refused` или таймаут | Проверь правильность порта, состояние процесса и путь из сети ПК |

Проверяй обычное действие целиком. Если у сайта есть чтение и сохранение данных, ответ главной страницы подтверждает только её. Для протокола без HTTP используй штатный клиент из задания.

### 6.2 Сначала выясни назначение порта, потом трогай фаервол

`ufw` — интерфейс к правилам фильтрации на Linux. Docker может публиковать порты через свои цепочки и перенаправлять пакеты раньше обычных правил UFW. `DOCKER-USER` относится к конфигурации Docker с backend iptables. На системах с другим backend порядок и способ задания правил могут отличаться.

Без изменения правил можно посмотреть текущее состояние:

```bash
sudo ufw status verbose
sudo iptables -S DOCKER-USER
```

Вторую команду используй на машине с подходящим backend, отсутствие цепочки бывает ожидаемо. Копировать массовое включение UFW или общее правило DROP из короткого файла рискованно: можно лишиться SSH или доступа чекера. Для подтверждённо ненужного порта сначала запиши, какая служба его открывает, нужен ли он игре и как вернуть настройку. Меняй один конкретный параметр с открытой консолью или запасной SSH-сессией и перепроверяй доступ. Общее правило на шлюз `10.2.X.1` не позволяет отличать команды по исходному адресу.

## 7. 10:25–10:35 — сохрани то, что понадобится для отката

Бэкап полезен, если ты знаешь **что в нём, куда это возвращать и как проверить после восстановления**. Для сервиса обычно нужны: код, конфиги, описание запуска, данные. Если нужно поменять один файл, создай также отдельную копию этого файла с исходным путём.

### 7.1 Упакуй каталог и проверь архив

На **vulnbox**, под учёткой, которой будешь скачивать. Пример для каталога `/opt/notes`:

```bash
umask 077
mkdir -p "$HOME/ad-backup"
df -h "$HOME" /opt
archive="$HOME/ad-backup/notes-before-$(date +%Y%m%d-%H%M%S).tar.gz"

sudo tar -C /opt -czf - notes > "$archive" &&
  tar -tzf "$archive" > /dev/null &&
  sha256sum "$archive"
printf '%s\n' "$archive"
```

1. `umask 077` делает новые файлы закрытыми для остальных пользователей в этом сеансе. `mkdir` создаёт каталог, `df -h` показывает свободное место.
2. `archive=...` сохраняет путь в переменную, часть `$(date ...)` добавляет время к имени.
3. `tar -C /opt` переходит в `/opt` для архивирования. `-c` создаёт архив, `-z` сжимает gzip, `-f -` направляет результат в стандартный вывод. `> "$archive"` сохраняет этот вывод в файл под твоей учёткой.
4. `tar -tzf` проверяет, что список файлов читается. `> /dev/null` скрывает длинный список. `sha256sum` печатает контрольную сумму архива.
5. Последняя команда показывает имя файла для скачивания. Если первый блок завершился с ошибкой или хеш не появился, эту попытку считай неудачной. Проверь путь, место и права, затем сделай новую копию.

### 7.2 Скачай на ПК и сравни хеши

**Где:** на ПК. Подставь **точное имя файла из прошлого шага**:

```bash
mkdir -p -m 700 ad-backup
scp -P 22 -i "$HOME/.ssh/ctf_ed25519"   player@10.2.17.2:ad-backup/notes-before-20261121-102800.tar.gz ./ad-backup/
sha256sum ./ad-backup/notes-before-20261121-102800.tar.gz
```

В `scp` порт указывается заглавной `-P`, в `ssh` — строчной `-p`. Аргумент перед `./ad-backup/` означает удалённый файл относительно домашнего каталога `player`. `./ad-backup/` — папка на ПК относительно текущего каталога. Сравни длинные шестнадцатеричные строки на сервере и ПК. Они должны совпасть полностью. В PowerShell аналог проверки — `Get-FileHash .\ad-backup\ИМЯ_ФАЙЛА -Algorithm SHA256`. Запиши путь к локальной копии.

### 7.3 Отдельно сохрани данные

| Где лежат данные | Как действовать |
|---|---|
| Каталог приложения | Убедись, что каталог реально попал в архив |
| Bind mount | `docker inspect` показывает путь на хосте и путь внутри контейнера. Сохрани данные из нужного каталога хоста |
| Именованный Docker-том | Зафиксируй имя и крепление тома. Делай бэкап штатным способом Docker или приложения. Архив проекта Compose отдельные тома не включает |
| PostgreSQL | Используй `pg_dump` с разрешённой учёткой и корректным адресом БД. Если база в контейнере, место запуска клиента и параметры подключения зависят от раскладки |
| SQLite | Используй команду `.backup` через клиент `sqlite3`. При включённом WAL часть актуальных данных может находиться вне основного файла |

Ниже примеры **на машине, с которой есть штатный доступ к базе**. Подставь имя своей базы и пути. Дампы сохраняй в закрытом каталоге.

```bash
umask 077
pg_dump -Fc -d DBNAME > "$HOME/ad-backup/notes.dump" &&
  pg_restore -l "$HOME/ad-backup/notes.dump"
```

`-Fc` выбирает архивный формат PostgreSQL. `pg_restore -l` читает оглавление и ничего не восстанавливает. Если `pg_dump` упал, наличие файла не доказывает успешный дамп. Скачай успешный дамп тем же способом, что архив.

```bash
sqlite3 /path/to/app.db ".backup '$HOME/ad-backup/notes.sqlite3'"
```

`.backup` просит SQLite создать согласованную копию. Подставь реальный путь к существующей базе, сначала проверь его. При восстановлении живого сервиса из старого дампа могут пропасть записи, сделанные после копирования. Если сломался только конфиг, верни только конфиг.

### 7.4 Одна правка — одна проверка

1. **Запиши исходное состояние.** Время, имя сервиса, его команда запуска, порт и результат штатного теста.
2. **Сохрани редактируемый файл.** Укажи полный путь. Сделай копию под уникальным именем вне путей автоподхвата, если сервис читает все файлы каталога.
3. **Внеси одно изменение.** Так проще связать сбой с его причиной. Если читаешь код для защиты, проследи, где обрабатываются входные данные, проверяются права и включён отладочный режим.
4. **Проверь синтаксис штатной командой приложения**, если она есть. Команда зависит от самого сервиса.
5. **Примени изменение по инструкции сервиса.** Снова выполни штатный тест с ПК. Посмотри логи за время правки. Если пользовался Compose, проверь состояние конкретного сервиса в соответствующем проекте.
6. **При сбое верни последнее изменение.** Повтори тот же способ применения настроек и тот же штатный тест. Запиши результат, чтобы другой участник не повторил проблемную правку.

## 8. 10:35–10:40 — проверь готовность

- [ ] С ПК открывается **новая** SSH-сессия по ключу, нужная учётка может пользоваться `sudo`. Известен способ входа через консоль.
- [ ] Вход по паролю проверен отдельно. При `Match` проверены настройки для конкретной учётки и адреса клиента.
- [ ] По всем игровым сервисам записаны порты и результаты штатных действий до и после правок.
- [ ] Архивы читаются. На ПК есть копии и сверены хеши. Понятно, где лежат данные каждого сервиса.
- [ ] Один человек смотрит Jury и знает, кто отвечает за последний патч каждого сервиса.

**Если времени осталось совсем мало:** в первую очередь проверь новый вход по ключу и штатную работу сервисов. Потом скачай уже готовые копии. Сложные правки без понятного отката оставь на момент, когда будет время проверить последствия.

| Симптом | Первый шаг |
|---|---|
| SSH таймаутит | Сверь сеть, IP и порт, через консоль проверь слушающий сокет |
| `Permission denied (publickey)` | Сверь логин и ключ, через рабочий сеанс проверь владельца, права, `AuthorizedKeysFile` и `Match` |
| `sshd -t` прошёл, после reload вход пропал | Через вкладку A восстанови изменённые файлы или убери новый drop-in, снова проверь конфиг и примени |
| Сервис открывается только на сервере | Сверь адрес прослушивания, опубликованный порт Docker и сетевые настройки |
| Jury показывает `DOWN` | Сначала проверь, доступен ли порт и жив ли процесс |
| Jury показывает `MUMBLE` | Проверь штатный сценарий целиком, затем свежие логи |
| Jury показывает `CORRUPT` | Проверь старые данные, нужный том и подключение к правильной БД |
| Jury недоступен до открытия сети | Продолжай локальные проверки и повтори после объявления площадки |
