# Шпаргалка по Attack-Defense CTF

## Как устроен формат Attack-Defense CTF

Каждая команда получает одинаковый набор уязвимых сервисов на своём хосте (vulnbox/vulnhost), доступном обычно по SSH или VPN. Задача двойная: чинить свои сервисы (defence) и ломать такие же сервисы у других команд (attack), пока они ещё не пропатчены.

- **Раунды (tick)** — обычно 1–5 минут. Каждый раунд система жюри кладёт в каждый сервис каждой команды новый флаг и в конце раунда (или через несколько раундов) проверяет, что флаг ещё можно прочитать — это SLA (service level agreement).
- **Checker** — скрипт жюри, который на каждом раунде делает `put(flag)` и `get(flag)` на сервис плюс базовую проверку функциональности (регистрация, обычные запросы). Если чекер не проходит — команда теряет очки за uptime/SLA по этому сервису в этом раунде, даже если её никто не взломал.
- **Flag id** — публичный идентификатор (обычно в ответе `put`), по которому эксплойт ищет, *где именно* у жертвы лежит флаг (id пользователя, номер заметки, имя файла и т.п.). Флаги без привязки к flag id искать сложнее — обычно придётся перебирать записи сервиса.
- **Flag format** — обычно регулярка вида `[A-Za-z0-9+/=]{30,40}==` или подобная; сдать можно только флаг, подходящий под формат и ещё не протухший (протухает через несколько раундов).
- **Submit-система** — отдельный сервис (TCP-сокет или REST), куда пачками шлются украденные флаги. Он возвращает статус по каждому: accepted / invalid / already submitted / too old / own flag.
- **Очки** обычно складываются так: *defence* (сервис был жив и отдавал флаги весь раунд) + *attack* (сколько чужих флагов сдано) − *штрафы* за падения/даунтайм. На части ивентов очки за атаку делятся между всеми, кто украл флаг у конкретной жертвы в раунде (чем раньше нашёл баг — тем больше очков).
- **Публикация трафика** — многие ивенты с задержкой (обычно на один-два раунда) публикуют pcap чужого трафика. Это значит: если кто-то эксплуатирует 0-day раньше вас, вы можете увидеть эксплойт в дампе и переиспользовать его («sniff & reuse») — отсюда важность снифать весь свой входящий/исходящий трафик с первой минуты.

## Инструменты и чеклист первого часа

**Набор инструментов, который стоит иметь под рукой до старта:**

| Категория | Инструменты |
| --- | --- |
| Трафик / сеть | tcpdump, tshark/Wireshark, nmap, netcat, mitmproxy |
| Веб | Burp Suite / OWASP ZAP, curl, sqlmap, ffuf/gobuster |
| Бинарники / pwn | gdb + pwndbg или gef, objdump, checksec, ghidra / IDA, pwntools, ropper/ROPgadget |
| Автоматизация атаки | Python (requests, pwntools), multiprocessing/asyncio для параллельных атак по всем IP |
| Разное | git (для диффа патчей), docker, tmux/screen, jq |

**Чеклист первых 60 минут:**

1. Получить доступ к vulnbox и сразу сделать **бэкап всех сервисов** (бинарники, исходники, конфиги) до любых изменений — если патч сломает сервис, нужно уметь откатиться.
2. Запустить `tcpdump -i any -w round_%Y%m%d_%H%M.pcap` на портах всех сервисов — трафик пригодится и для поиска чужих эксплойтов по себе, и как доказательство атаки.
3. Пройтись по списку сервисов: язык/стек, порты, что именно делает чекер (какой put/get запрос), где лежат флаги.
4. Быстрый грубый аудит кода на явные маркеры уязвимостей — ниже команды для grep:

```
grep -rnE "exec\(|eval\(|system\(|popen\(|pickle\.loads|unserialize\(|yaml\.load\(|ObjectInputStream" .
grep -rnE "strcpy|strcat|sprintf|gets\(|memcpy" .   # C/C++
grep -rnE "query\(.*\+|f\"SELECT|execute\(.*%" .     # конкатенация в SQL
```

5. Патчить **только** то, что подтверждено как уязвимость, и сразу проверять, что чекер всё ещё проходит (если есть локальная копия чекера — гонять его после каждого патча; если нет — руками повторить его обычный сценарий put/get).
6. Поднять свой health-check (cron раз в раунд), который дёргает сервис так же, как чекер — чтобы узнать о падении раньше жюри.
7. Как только найдена рабочая уязвимость — сразу писать скрипт атаки, который бьёт **по всем IP соперников параллельно**, а не руками по одному.
8. Следить за scoreboard: резкое падение defence-очков по сервису = скорее всего кто-то нашёл баг, который вы ещё не запатчили.

## Веб-уязвимости: паттерны, эксплуатация, патч

В AD CTF веб-сервисы чаще всего ломаются через один из классов ниже. Для каждого — как выглядит уязвимый код, как это эксплуатируется и как чинить, не ломая легитимную функциональность (чекер часто дергает те же самые ручки).

### SQL Injection

PHP + MySQLi (конкатенация строки в запрос):

```php
$res = mysqli_query($conn, "SELECT * FROM users WHERE login='".$_POST['login']."' AND pass='".$_POST['pass']."'");
```

Эксплуатация — обход логина через `login`: ` admin' --  ` (всё после `--` комментируется), или через UNION для чтения чужих данных: ` ' UNION SELECT flag,2,3 FROM secrets--  `.

**Патч:** параметризованные запросы (prepared statements), никогда не склеивать пользовательский ввод в SQL-текст:

```php
$stmt = mysqli_prepare($conn, "SELECT * FROM users WHERE login=? AND pass=?");
mysqli_stmt_bind_param($stmt, "ss", $_POST['login'], $_POST['pass']);
```

SQL-инъекции остаются одним из самых часто встречающихся классов багов в AD CTF — сервисы с похожей конкатенацией строк в запросе регулярно попадаются на крупных ивентах вроде ENOWARS, saarCTF или RuCTFE.

### Command Injection

Python, запуск shell с пользовательским вводом:

```python
import os
os.system("ping -c 1 " + request.form['host'])
```

Эксплуатация — инъекция через `;`, `&&`, `|`, обратные кавычки/подстановку: `host=1.1.1.1; cat /flag.txt` или `` host=`cat /flag.txt` ``.

**Патч:** не вызывать shell вообще — `subprocess.run(["ping","-c","1",host], shell=False)` со списком аргументов, плюс строгая валидация ввода (например, регэксп на IP).

Реальный пример: в финале Cyber Jawara 2018 (формат Attack-Defense) сервис p04-coderunner принимал от игрока файл с кодом и выполнял его, чтобы посчитать контрольную сумму посылки — случай, когда выполнение пользовательского кода было частью задумки, а не багом; такие сервисы требуют особенно строгой песочницы (отдельный контейнер с минимальными правами, лимиты по времени и памяти на выполнение).

### Path Traversal / LFI

Node.js, путь собирается из параметра:

```javascript
app.get('/file', (req, res) => {
  res.sendFile(path.join(__dirname, 'uploads', req.query.name));
});
```

Эксплуатация: `?name=../../../../etc/passwd` или на Windows `..\..\..\windows\win.ini`; в PHP с `include($_GET['page'])` то же самое плюс возможность получить RCE через LFI → log poisoning (подставить PHP-код в User-Agent, который попадёт в лог веб-сервера, а затем инклюднуть лог-файл).

**Патч:** нормализовать путь (`path.normalize`/`realpath`) и явно проверять, что итоговый путь остаётся внутри разрешённой директории (`startsWith` на уже резолвленном абсолютном пути), плюс white-list разрешённых имён файлов, если это возможно.

Реальный пример: сервис Piano на ENOWARS 3 (PHP) содержал путь-траверсал — сама уязвимость была несложной, основная сложность заключалась в разборе формата: флаги там прятали стеганографией в MIDI-файлах.

### SSTI (Server-Side Template Injection)

Flask/Jinja2, когда пользовательский ввод попадает прямо в шаблон:

```python
from flask import render_template_string
return render_template_string(f"Hello {request.args['name']}!")
```

Эксплуатация: `?name={{7*7}}` вернёт `49` — подтверждает инъекцию, дальше можно дойти до RCE через цепочку `{{ self.__init__.__globals__.__builtins__.__import__('os').popen('cat /flag').read() }}`.

**Патч:** никогда не передавать пользовательский ввод в сам шаблон — только как переменную контекста: `render_template_string("Hello {{ name }}!", name=request.args['name'])` (Jinja2 авто-экранирует значение, а не исполняет его как код шаблона).

Шаблонизаторы (особенно Jinja2 в Python-сервисах) — частый источник SSTI в подобных играх, если разработчики в спешке рендерят пользовательский текст напрямую вместо того, чтобы передавать его как переменную контекста.

### Insecure Deserialization

PHP (`unserialize` на пользовательских данных) и Python (`pickle.loads`) выполняют произвольный код при десериализации специально собранного объекта, если в классах есть "магические" методы (`__wakeup`, `__destruct` в PHP; `__reduce__` в Python):

```php
$data = unserialize($_COOKIE['session']); // класс с __destruct(), который пишет файл или выполняет команду — готовый гаджет для RCE
```

```python
import pickle, base64
obj = pickle.loads(base64.b64decode(request.cookies['session']))  # __reduce__ любого класса выполнится при loads()
```

Эксплуатация: найти в кодовой базе класс с подходящим магическим методом ("гаджет"), сериализовать объект этого класса с нужными полями — при десериализации на сервере сработает его метод.

Патч: не десериализовать недоверенные данные в принципе, перейти на JSON или MessagePack без исполняемых гаджетов; если формат менять нельзя — подписывать сериализованные данные (HMAC) и проверять подпись до unserialize/pickle.loads.

Pickle-сериализация в Python и стандартная сериализация в Java всплывают почти на каждом крупном AD CTF хотя бы в одном сервисе — обычно там, где состояние пытались "по-быстрому" сохранить в cookie или файл.

### XXE (XML External Entity)

Python, парсер по умолчанию резолвит внешние сущности:

```python
from lxml import etree
tree = etree.parse(request.data)  # resolve_entities=True по умолчанию в старых версиях
```

Эксплуатация: атакующий присылает XML, где в DOCTYPE объявлена внешняя сущность со ссылкой на файл сервера (например file:///flag.txt), а в теле документа эта сущность используется — парсер подставляет в ответ содержимое файла.

Патч: явно отключить внешние сущности и DTD при создании парсера — etree.XMLParser(resolve\_entities=False, no\_network=True); в Java — включить feature disallow-doctype-decl у DocumentBuilderFactory.

XXE чаще встречается там, где сервис явно работает с XML или SOAP — такие сервисы реже пишут с нуля, и в стороннем XML-парсере легко забыть явно отключить внешние сущности.

### IDOR / Broken Access Control

Самый частый баг в AD CTF — ручка берёт id из запроса и отдаёт объект без проверки, что он принадлежит текущему пользователю: запрос вида GET /api/notes/142 просто отдаёт заметку номер 142 тому, кто её запросил, без всякой проверки владельца.

Эксплуатация — обычный перебор id (1, 2, 3…) чужими запросами; так чаще всего воруют флаги, лежащие в заметках, сообщениях или профилях других пользователей.

Патч: на каждой ручке, отдающей объект по id, явно проверять object.owner\_id == current\_user.id, а не полагаться на то, что id "трудно угадать".

Реальный пример: сервис Shittr (клон Twitter) на ENOWARS 3 показывал приватные сообщения любому, кто их запросит, но в ответе они выглядели как длинная base64-строка — разработчики перепутали кодирование с шифрованием: base64 обратим без всякого ключа, так что это был прямой доступ к чужим приватным данным под видом "защищённых".

### SSRF (Server-Side Request Forgery)

Python, сервис сам ходит по URL, который дал пользователь:

```python
import requests
resp = requests.get(request.args['url'])  # пользователь может указать внутренний адрес вроде 127.0.0.1/admin или 169.254.169.254
return resp.text
```

Эксплуатация: запросить ?url=http://127.0.0.1:6379/ (внутренний Redis или админку, недоступную снаружи) или адрес облачных метаданных 169.254.169.254 — сервис сходит туда от своего имени и вернёт ответ атакующему.

Патч: резолвить хост и явно блокировать loopback и приватные диапазоны (127.0.0.0/8, 10.0.0.0/8, 169.254.0.0/16 и подобные) до запроса, либо держать белый список разрешённых хостов.

### JWT и слабая аутентификация

Типичные баги: сервер принимает токен с alg равным none без подписи, либо секрет для HMAC — короткая строка или дефолт из примера фреймворка, который легко перебрать офлайн.

Эксплуатация: взять любой валидный токен, заменить заголовок на алгоритм none и убрать подпись (третий, последний сегмент токена) — часть библиотек по-прежнему примет такой токен как действительный.

Отдельный частый случай — дефолтные или захардкоженные учётные данные (admin/admin, тестовый пользователь из примера фреймворка), которые забыли убрать перед деплоем; стоит проверять их в первую очередь, до поиска более сложных багов.

Патч: явно разрешать только ожидаемый алгоритм при верификации (jwt.decode(token, key, algorithms=\['HS256'\]), никогда не брать alg из самого токена), использовать длинный случайный секрет.

## Бинарные (pwn) уязвимости на C

### Переполнение буфера на стеке

```c
void vuln(char *input) {
    char buf[64];
    strcpy(buf, input);
}
```

strcpy не проверяет длину input: если она превышает размер buf, запись выходит за границы буфера и может переписать сохранённый адрес возврата на стеке — выполнение программы можно перенаправить на код атакующего (shellcode) или на существующий код программы (ROP-цепочка), если на бинарнике включены защиты, запрещающие исполнение данных на стеке.

**Патч:** заменить strcpy на функцию с явным лимитом по размеру buf (strncpy, или лучше snprintf), либо проверять длину input до копирования.

### Format string vulnerability

```c
void log_input(char *input) {
    printf(input);
}
```

Если пользовательская строка попадает прямо в printf как формат, атакующий через спецификаторы %x может читать данные со стека, а через %n — писать по произвольному адресу.

**Патч:** всегда передавать формат отдельно от данных: printf("%s", input).

### Use-after-free и целочисленное переполнение (кратко)

Use-after-free: память освобождена через free, но указатель на неё продолжает использоваться. Если атакующий успевает выделить на то же место контролируемые данные (heap grooming), он может подменить содержимое структуры, на которую всё ещё ссылается "висячий" указатель.

Integer overflow: размер буфера считается через арифметику над пользовательским вводом (например сложение или умножение двух чисел от пользователя) без проверки переполнения типа — в итоге выделяется буфер меньше, чем предполагалось, и последующая запись в него переполняет кучу.

**Патч для обоих:** обнулять указатель сразу после free; проверять переполнение перед арифметикой над размерами, не доверять пользовательским числам при вычислении размеров выделения.

### Базовые защиты бинарников

| Защита | Что делает | Как проверить |
| --- | --- | --- |
| Stack canary | Случайное значение перед адресом возврата, проверяется при выходе из функции | checksec по бинарнику |
| NX / DEP | Запрещает исполнение кода на стеке и куче, заставляет переходить на ROP вместо shellcode | checksec |
| ASLR | Рандомизирует адреса библиотек и стека между запусками | значение randomize\_va\_space в настройках ядра хоста |
| PIE | Рандомизирует адрес загрузки самого бинарника | checksec |

На AD CTF обычно дешевле пропатчить исходный код и устранить саму уязвимость, чем полагаться на защиты бинарника — они усложняют эксплуатацию, но не убирают баг, и соперники рано или поздно найдут способ их обойти, если сам баг остался.

## Типичные крипто и логические баги

### Криптографические баги

- **Самописная крипто** — свой "шифр" (часто простой XOR с коротким повторяющимся ключом) вместо проверенного алгоритма; XOR с коротким ключом ломается частотным анализом или известным открытым текстом.
- **ECB-режим** у блочных шифров — одинаковые блоки открытого текста дают одинаковые блоки шифротекста, видны повторяющиеся паттерны, блоки можно переставлять местами (block reordering).
- **Хардкод ключей и секретов** прямо в исходниках или конфигах образа — достаточно прочитать бинарник/исходник, чтобы получить ключ для всех команд сразу.
- **Предсказуемый источник случайности** — сид от time() или обычный rand() вместо криптографически стойкого генератора, что позволяет предсказать токены сессии или сброса пароля.
- **Пароли без соли** на устаревших хешах (md5/sha1) — позволяют быстро перебрать по радужным таблицам.

**Патч:** использовать проверенные примитивы (AES-GCM или ChaCha20-Poly1305 для шифрования с аутентификацией, bcrypt/argon2/scrypt для паролей), генерировать секреты и соли через криптографически стойкий генератор (os.urandom/secrets в Python), никогда не писать свою крипто с нуля.

### Логические баги

- **Race condition (TOCTOU)** — проверка состояния (баланс, права, остаток товара) происходит отдельно от самого действия; два параллельных запроса проходят проверку одновременно и оба проходят, хотя по отдельности каждый не должен был пройти (классика — двойной перевод с одного и того же баланса).
- **Отсутствие валидации диапазона/знака** — например можно "купить" товар дешевле, отправив отрицательное количество, или пропустить шаг оплаты, обратившись сразу к следующему эндпоинту воркфлоу.
- **Слабый или отсутствующий rate-limit** на чувствительных действиях (подбор PIN-кода, пароля, токена сброса).

**Патч:** оборачивать последовательность "проверить-затем-сделать" в одну транзакцию с блокировкой строки (или mutex/lock на уровне приложения), валидировать входные числа на знак и диапазон, добавлять rate-limit и задержки на чувствительные эндпоинты, проверять порядок шагов воркфлоу на сервере, а не полагаться на то, что клиент пойдёт по шагам по порядку.

## Как патчить сервис в бою, не сломав его и checker

1. **Бэкап перед любым патчем** — сохранить текущие бинарники, исходники и конфиги/образ до изменений, чтобы откатиться за секунды, если патч что-то сломает.
2. **Минимальный диф** — менять только уязвимую строку или функцию, не рефакторить всё подряд: чем меньше изменений, тем меньше риск незаметно сломать то, на что полагается checker.
3. **Проверять патч поведением checker'а, а не на глаз** — если есть локальная копия официального checker-скрипта, прогонять её после каждого патча (put/get/putnoise/getnoise); если копии нет, вручную повторить тот же сценарий запросов, который виден в трафике жюри в первых раундах или в описании сервиса.
4. **Способы быстро закрыть дыру без полного передеплоя:**
   - В интерпретируемых языках (PHP/Python/Node) — правка файла на лету и перезапуск процесса или воркеров без пересборки образа.
   - В скомпилированных бинарниках — патч нужных байт прямо в файле (hex-patch инструкции или строки) или LD\_PRELOAD с подменённой функцией (например безопасная версия strcpy вместо обычной) — быстрее, чем пересобирать и передеплоивать весь сервис.
   - Правило на прокси/WAF (например фильтр в nginx или lua-скрипт), блокирующее конкретный паттерн payload — закрывает дыру за секунды, пока готовится нормальный патч в коде; минус такого способа — легко обходится, если атакующий чуть изменит payload.
5. **Не выключать снифинг трафика после патча** — продолжать писать pcap, чтобы видеть новые попытки эксплуатации той же дыры у других команд и убедиться, что патч действительно держит.
6. **Если патч уронил SLA** — выгоднее откатиться на бэкап и чинить спокойнее, чем копить штрафы за даунтайм несколько раундов подряд.

## Как писать эксплойт для атаки других команд

Типичный эксплойт — скрипт, который принимает хост жертвы (и, если нужно, flag\_id) аргументом, подключается к сервису, воспроизводит шаги уязвимости и печатает украденный флаг в stdout.

Шаблон для веб-сервиса (Python + requests):

```python
import sys, requests

def exploit(host, flag_id):
    url = f"http://{host}:8080/api/notes/{flag_id}"
    r = requests.get(url, timeout=5)
    if r.ok:
        print(r.json()["content"])  # ожидаем, что тут окажется флаг

if __name__ == "__main__":
    exploit(sys.argv[1], sys.argv[2])
```

Шаблон для pwn-сервиса (pwntools):

```python
from pwn import remote

def exploit(host):
    io = remote(host, 9999)
    io.sendline(payload)  # payload собирается заранее под конкретный баг
    print(io.recvline())
```

**Ключевые практики:**

1. **Параллелизация по всем целям** — не гонять эксплойт руками по одной команде, а запускать по списку всех соперников параллельно (multiprocessing.Pool или asyncio) и сдавать флаги пачкой в submit-систему.
2. **Автоматизация через "ферму"** — инструменты вроде DestructiveFarm берут на себя рассылку эксплойта по всем целям, повторные попытки, сдачу флагов и статистику — не нужно писать это руками под каждую игру заново.
3. **Поиск flag\_id** — если флаг привязан к идентификатору (имя заметки, id пользователя и т.п.), его обычно видно в собственном трафике от checker'а (в put-запросе) или можно получить из публикуемого жюри дампа трафика.
4. **Sniff and reuse** — если кто-то другой нашёл баг раньше вас, его эксплойт будет виден в опубликованном pcap; скрипт, который парсит дамп и вычленяет payload из чужих атак, экономит время на самостоятельный поиск той же уязвимости.
5. **Не ломать сервис жертвы** — эксплойт должен только читать флаг, не писать туда мусор и не создавать нагрузку, похожую на DoS: это обычно запрещено правилами ивента и ведёт к штрафам или дисквалификации.

## Открытые репозитории прошлых Attack-Defense CTF

Лучшая тренировка перед игрой — поднять у себя локально реальные сервисы прошедших игр и попробовать самому найти баг, пропатчить и написать эксплойт, пока не тикает таймер.

- **saarCTF** (команда saarsec, один из сильнейших составов в AD CTF) — репозитории с сервисами, чекерами и демо-эксплойтами за разные годы: [saarctf-2025](https://github.com/saarsec/saarctf-2025), [saarctf-2022](https://github.com/saarsec/saarctf-2022), [saarctf-2020](https://github.com/saarsec/saarctf-2020). В той же организации лежит и игровая инфраструктура (gameserver, инструменты сборки vulnbox) — пригодится, если захотите поднять у себя полноценный полигон.
- **ENOWARS** — ежегодный ивент от той же команды; фреймворк для чекеров на Python называется [enochecker](https://github.com/enowars/enochecker), в нём видно структуру putflag/getflag/putnoise/getnoise/havoc, по которой строятся реальные чекеры.
- **International Cybersecurity Challenge (ICC)** — сервисы и материалы прошедших игр: [ICC2022-AD-CTF](https://github.com/CybersecNatLab/ICC2022-AD-CTF).
- **Cyber Jawara** (Индонезия) — сервисы финала 2018 года на Docker с классическими веб-багами (LFI, небезопасный eval и подобное): [CJ2018-Final-CTF](https://github.com/farisv/CJ2018-Final-CTF).
- **Инфраструктурные инструменты**, которые реально используются на таких играх — есть смысл развернуть заранее, чтобы не разбираться в них во время игры:
  - [DestructiveFarm](https://github.com/DestructiveVoice/DestructiveFarm) — ферма для автоматической рассылки эксплойта по всем командам и сдачи флагов.
  - [Tulip](https://github.com/OpenAttackDefenseTools/tulip) — анализатор трафика: разбор pcap, поиск и повтор чужих атак.
  - [ataka](https://github.com/OpenAttackDefenseTools/ataka) — ещё один раннер эксплойтов с консольным клиентом для игроков.
- **ctftime.org** — календарь и архив прошедших ивентов; на странице каждого AD CTF обычно есть ссылки на райтапы участников с разбором конкретных уязвимостей сервисов того года.

Список не исчерпывающий — стоит поискать также RuCTF/RuCTFE и DEFCON CTF Qualifier/Finals (оба играются в формате attack-defense); у многих организаторов исходники сервисов выкладываются в открытый доступ через несколько месяцев после ивента.

## Итоговый чеклист на день соревнования

- [ ] Выспаться перед игрой — AD CTF обычно идёт 8–12+ часов, уставшая команда теряет больше очков на своих же ошибках в патчах, чем пропускает атак.
- [ ] Проверить и собрать весь набор инструментов из раздела про инструменты заранее, не во время игры.
- [ ] Распределить роли в команде: кто патчит веб-сервисы, кто разбирает pwn, кто пишет и гоняет эксплойты, кто следит за scoreboard и трафиком.
- [ ] Подготовить шаблоны заранее: health-check скрипт, шаблон эксплойта под веб и под pwn, скрипт параллельной атаки по всем IP, набор grep-команд для быстрого аудита кода.
- [ ] Сразу после получения доступа к vulnbox — бэкап всех сервисов до каких-либо изменений.
- [ ] С первой минуты — tcpdump на все порты сервисов, без перерывов.
- [ ] Патчить только подтверждённые уязвимости и проверять каждый патч поведением checker'а, а не на глаз.
- [ ] Как только эксплойт заработал — сразу автоматизировать атаку по всем командам параллельно, не ходить руками по одной.
- [ ] Следить за scoreboard и логами весь день — резкое падение defence-очков почти всегда значит, что кто-то нашёл новый баг, который ещё не пропатчен.
- [ ] Держать план отката: если патч ломает сервис — откатиться на бэкап, а не чинить под огнём во время раунда.
